# Local development

For contributors running the full Clew application. Connector authors can start with the [connector quickstart](../guides/creating-a-connector.md), whose first check needs no running services.

Host commands below start Docker infrastructure; application commands run inside `clew-app-1` at `/workspace`. These instructions use a local Keycloak, either the shared container on macOS or the stack's own (the `keycloak` profile), and are not a production deployment recipe.

## Run it

Everything runs in Docker. Commands go through `docker exec` into the app container (Claude Code and most editors sit outside the devcontainer).

```sh
sh scripts/compose.sh up -d --build --wait app postgres   # app image (Node 26.13.0 LTS + Bun 1.4.4) and Postgres 17
docker exec -w /workspace clew-app-1 bun install --frozen-lockfile
docker exec -w /workspace clew-app-1 bun run db:init     # Drizzle migrations
docker start keycloak                                    # macOS: the shared local Keycloak 26.2 at keycloak.orb.local:8090
docker inspect keycloak --format '{{json .Config.Env}}' | docker exec -i -w /workspace clew-app-1 bun run auth:setup
sh scripts/calendar.sh start                             # Nextcloud CalDAV provider + Mailpit, seeded with synthetic people and meetings
docker exec -it -w /workspace clew-app-1 bun run dev                 # BFF on :3000 and Vite on :5173, published as http://localhost:3020
```

Without the shared container (Windows, Linux, or by choice), the stack runs its own Keycloak (D62). Use these two lines in place of the two Keycloak lines above:

```sh
sh scripts/compose.sh --profile keycloak up -d --wait app postgres keycloak
docker inspect clew-keycloak-1 --format '{{json .Config.Env}}' | docker exec -i -e KEYCLOAK_PUBLIC_URL=http://keycloak.localhost:3024 -w /workspace clew-app-1 bun run auth:setup
```

Later runs of `auth:setup` keep that address from `.env.local`. Start the stack with the profile from then on (`sh scripts/compose.sh --profile keycloak up -d --wait`).

Open http://localhost:3020. Synthetic accounts: `hillevi` (rektor, manager persona), `hassan` (undersköterska, employee persona) and `mikael` (systemförvaltare, `admin.connectors`). Each has a Nextcloud calendar; `calendar.sh seed` gives all three a week of meetings. Passwords are generated by `auth:setup` into the ignored `.auth-test.env`; the BFF reads `apps/server/.env.local`, also ignored.

### The Keycloak address (D60, D62)

The issuer must be the same address for the browser and for the BFF in the app container. `auth:setup` takes it from `KEYCLOAK_PUBLIC_URL`, then from the issuer already in `apps/server/.env.local`, and falls back to `http://keycloak.orb.local:8090`, OrbStack's name for a container called `keycloak` on macOS. Plain HTTP is accepted only when the issuer has a loopback name (`localhost`, `127.0.0.1`, `[::1]`, `*.localhost` or `keycloak.orb.local`); `auth:setup` refuses any other HTTP address.

- **The shared Keycloak on macOS.** The app container maps `keycloak.orb.local` to the host, where the container answers.
- **The stack's own Keycloak** (`keycloak` profile). It shares the app container's network, so `keycloak.localhost:3024` is loopback for everyone: the browser on the host through the port the app service publishes, Node, Bun and curl inside the container. `auth:setup` then reaches its admin API on that address and gives Keycloak `http://127.0.0.1:3000` for back-channel logout.
- **After the app container restarts on its own** (a `docker restart`, or `compose up` without the profile recreating it), Keycloak is left in the old network and nothing reaches it, although its health check still passes. Restart it: `sh scripts/compose.sh --profile keycloak restart keycloak`.

### Windows with Docker Desktop

Verified on Windows 11 with Docker Desktop. Use the stack's own Keycloak (above); there is no shared container. Two more things differ from macOS:

- **Line endings.** Git for Windows checks files out with CRLF by default, which breaks the shell scripts that run in Linux containers (the calendar image's start hook among them). `.gitattributes` makes every checkout LF (D61), so a fresh clone needs nothing. A clone made before that file existed keeps CRLF until it is checked out again once: `git rm --cached -r -q . && git reset --hard`, on a clean tree, or a new clone.
- **Git Bash.** It rewrites `/workspace` in `docker exec -w /workspace …` into a Windows path. Run the commands from PowerShell, or prefix them with `MSYS_NO_PATHCONV=1` (also `sh scripts/calendar.sh start`, which calls `docker exec`).

On Linux with Docker Engine the stack's own Keycloak should work the same way, since it needs no route to the host, but that is not verified.

Checks:

```sh
docker exec -w /workspace clew-app-1 bun run check      # tsc + dependency rules (D20) + Bun unit tests + Node runtime tests; also runs in CI
docker exec -w /workspace clew-app-1 bun run test:node  # current server runtime, without external services
docker exec -w /workspace clew-app-1 bun run test:db    # PostgreSQL contracts
docker exec -w /workspace clew-app-1 bun run test:durability # PostgreSQL/Temporal/Node synthetic reliability scenarios
sh scripts/a11y.sh menu.spec.ts --timeout 15000         # on the host: the WCAG specs a change touches, failing fast (D51); the full suite runs by hand until the run-up to a release (D59)
sh scripts/a11y.sh                                      # the whole WCAG 2.2 AA suite, as the workflow runs it: about eight minutes, not a per-edit check
```

Ports on loopback: 3020 web, 3021 Nextcloud (`calendar-admin`), 3022 Mailpit, 3023 Temporal UI, 3024 Keycloak with the `keycloak` profile (`keycloak-admin`).

Temporal (server and UI) starts with the base compose stack and creates its two databases in the shared Postgres on first start. The BFF runs the worker in-process. Approved executions, reminder/snooze timers, bounded calendar follow-up and scheduled jobs use durable PostgreSQL intent before Temporal dispatch. A reminder keeps its absolute due time through an outage; queued/blocked states remain visible. Follow workflows in the UI at http://localhost:3023 and inspect aggregates with `docker exec -w /workspace clew-app-1 bun scripts/reliability-status.ts`. See [scheduled work](../architecture/scheduled-work.md) and the [operations runbook](reliability-operations.md).

The older login/connector smoke scripts assume synchronous source decisions; they are not acceptance evidence for the new asynchronous paths. See [testing](../architecture/testing.md) for the maintained suites and remaining live-source checks.

The calendar image refreshes its pinned Calendar and RoomVox code in an existing data volume before Apache starts, then runs Nextcloud's app migrations. Unchanged versions do nothing; a failed upgrade stays pending and is retried on restart. App downgrades are refused. Back up the calendar volume before applying upgrades; restoring older image pins alone does not undo database migrations.
