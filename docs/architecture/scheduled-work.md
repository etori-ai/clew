# Scheduled work

Current implementation: 2026-11-05, [D45](../decisions/D45-approved-intent-precedes-source-dispatch.md), [D46](../decisions/D46-browser-updates-use-committed-revisions.md) and [D47](../decisions/D47-occurrences-timers-and-attention-have-durable-identities.md). D15 records the historical Postgres-only scheduler rationale; D17 adopted Temporal and [D85](../decisions/D85-dbos-transact-replaces-temporal-as-the-durable-engine.md) replaced it with DBOS Transact inside the server. Node runs the server, and the engine with it. PostgreSQL owns business intent and evidence.

## Ownership and flow

| Work | Durable intent | Executor and safety boundary |
|---|---|---|
| Approved source write or compensation | Execution, encrypted input/result, audit, projection and the `approvedExecution` workflow start in one transaction | The workflow dispatches the exact approval; current authority, stable ID and read-back determine outcome |
| Reminder or snooze | Absolute due time, generation and desired state, committed with thread, audit and the `durableReminder` workflow start | Generation-specific workflow; activity rejects stale/cancelled generations and rechecks authority; a cancelled or replaced generation is cancelled after the commit, best effort |
| Calendar follow-up | Bounded policy plus obligation timer | Current invitation, actor/assignment and expiry checked before transactional cards/counters/audit |
| Job watch step ([D55](../decisions/D55-a-job-is-assembled-from-what-connectors-follow-approved-once-and-run-per-system.md)) | The step's absolute check times and window's end, committed with the job as a `watch_intent` row and its `jobWatch` workflow start | One `jobWatch` workflow per step waits for each check and calls `observe`, fenced by check index, step state and the ledger's clock; it rechecks authority and reads the step's own connector as the person, never an execute |
| Nightly scan, nightly sign-in clean-up ([D117](../decisions/D117-clew-empties-expired-sign-in-data-itself-and-a-leavers-retention-is-the-organisations-decision.md)), undo/receipt expiry, attention release | Natural-key job row and its `scheduledJob` workflow start, in one transaction | `scheduledJob` workflow; execution lease and attempt fences |
| Source refresh | Coalesced per-person/source/assignment request | Four workers, separate source deadlines, authority and projection-version fences |

A request succeeds when intent commits; it need not wait for a source. The workflow start is part of that commit (`dbos.enqueue_workflow` on the transaction's connection, D86): a rollback leaves no workflow, and a committed row waits in the application's ledger queue (`clew.ledger`) until an instance of the application dequeues it, about once a second while one runs, or when the next one launches. There is no outbox loop, no delivery lease and no queued state to show. Enqueueing is idempotent by workflow id, so a replayed approval meets the existing workflow. Workflows wait until absolute timestamps, so a late dequeue does not extend a requested duration.

Unknown writes remain unknown until evidence resolves them. A lost reply does not authorize replay. Calendar uses stable event UIDs, conditional revisions and per-item read-back; compensation requires an exact supported inverse of confirmed effects. This cannot promise arbitrary-source exactly-once behavior.

## Follow-up and old work

New calendar policies cap reminders at two per invitation, two working days apart and ending after 30 days. Policy is committed with approval; its first timer waits behind pending/uncertain execution before follow-up effects. Expiry still wins during uncertainty. Checks re-evaluate current authorization, assignment, invitation response, cancellation and members. A manual reminder consumes the same bound.

A job's watch step is the bounded conditional watch for a system Clew does not write in: at most three checks inside the follower's window, capped by the binding, and the window's end, all absolute and committed at approval. A late check is observed late, never repeated, and the window is never extended. `seen` ends the watch; a source that does not answer leaves it waiting for the next check; revoked or moved authority leaves it `blocked`; the window's end settles `expired` and, in the same commit, leaves one card for the person through the attention admission below ("Lönesystemet har inte visat det som bevakades"). A watch is approved once and never replaced, so its intent has one generation and the fence per fire is the check index; there is no cancel of a running watch.

Legacy invitations without such a policy are visibly paused. Workflow functions stay replay compatible across releases (D47; D85 item 2, as amended 2026-11-13), since an operator's move continues a workflow of an older release under the newer code from where its records end, and the engine refuses a replay whose recorded steps the code no longer calls, which ends the workflow in `ERROR`; legacy obligation callbacks cannot revive unbounded follow-up. Old running job owners become legacy-running until an operator establishes their outcome. See [upgrade and recovery](../maintainers/reliability-operations.md).

The application starts no polling runner at all: the nightly scan and the nightly sign-in clean-up are scheduled at boot, once the engine has launched, and every job row starts its workflow with its own insert. Each night's run schedules the next, so a night whose workflow a deployment left waiting under the replaced application version, which no process of the new one recovers (D85 item 2), would end its job's chain. The start takes over the last and the next night of each job instead, the last one being there when the deployment's downtime spanned its time. It cancels the night's workflow, which changes only the engine's records, and rewinds it to its first step under its own id and the running version; it rewinds a night that an earlier start cancelled and was stopped before rewinding, and leaves a night that another start moved meanwhile (`startNightly` and `seedNightly` in [the scheduler](../../apps/server/src/scheduler/usecases.ts), `moveToRunningVersion` in [the engine's start](../../apps/server/src/dbos/start.ts)). A last night taken over runs at once. Before its job's claim a night records only the clock and its wait, and the claim fences a second run, also one by a process of the older version that still sleeps on the night: the cancel does not stop that process, which may wake and run the night with its own code, and only its record of the step fails. Every other workflow left under an older version, and a night older than the last, is moved by an operator with `scripts/workflows-move.ts` from its first step without a record, and a workflow in `ERROR` is started again from the step that failed ([after every deployment](../maintainers/reliability-operations.md#after-every-deployment)). A job id is a natural key, such as `scan:2026-11-04` or `sign-in-cleanup:2026-11-05`, so scheduling it again is harmless. It never carries a person's name or user name, at most their id, as `attention:automatic:<personId>:<dueAt>` does, because it is written as `job:<id>` into the audit row's subject and into the workflow id on the engine's spans. The `scheduledJob` workflow sleeps until the run time and then runs its step, `scheduledJobRunner` in [the scheduler](../../apps/server/src/scheduler/usecases.ts) over the `JobExecutions` port (`durableJobs`): it claims the row under a 120-second lease with the attempt as fence, runs the job by its kind and completes it with a `job.completed` row; `busy` (before the run time, or under another lease) is asked again every 30 seconds. A new job kind is handled in `scheduler.run`.

The sign-in clean-up runs at 03:00 Stockholm time. It schedules the next night first, then deletes every session past either expiry, with an `expired` row in the authentication log for one that was still open, and deletes expired login transactions and logout receipts; it never deletes the authentication log. A night whose clean-up fails writes one error line, scope `scheduler`, `sign-in clean-up failed`, and still completes. The next night removes what was left, so a lasting failure gives one line a night and no workflow that keeps claiming its job.

The job table remains the evidence record, with the retired outbox's delivery columns left in place (D86). A trigger maps legacy due inserts to the engine's ownership (the status value is still spelled `temporal`), but deployment must stop already-running old workers before changing owners.

## Discovery and attention

Reads return persisted cards and request coalesced refresh. Failures affect the source's freshness, not availability of known work. Occurrences carry source identity/revision and local disposition; failed/partial snapshots cannot complete absent work. Calendar's synthetic planner keeps its separate proposal lifecycle.

Automatic attention commits with discovery and uses a Stockholm-day budget, five-minute coalescing, review/bundle windows and quiet hours. User reminders bypass the automatic budget. The signed-in shell claims persisted batches on every page; D46 SSE invalidates TanStack Query without browser polling.

An automatic delivery that quiet hours or the day's budget defers is written `waiting` in its batch, `automatic:<personId>:<dueAt>`. In the same transaction the batch's job is written through `scheduleJob` ([threads adapter](../../apps/server/src/threads/adapters/attention-postgres.ts)): id `attention:<batch>`, kind `attention-release`, run time the due time, with its `job.scheduled` row and its `scheduledJob` workflow (D86). One job and one workflow serve a batch; later deliveries of the batch add none. At the due time the durable engine runs the job's step, which makes the batch's waiting deliveries `ready`, audited as `attention.released` (actor `system:attention`, with the count), and completes the job. The admission reads the job row `FOR SHARE` until it commits: while the job is still the engine's to run (status `temporal`), the delivery is written `waiting`; once the job has been claimed, it is written `ready` with the batch's due time. A release that arrives while an admission of its batch is still open waits for that commit, because the claim's `FOR UPDATE` waits on the share lock, and the one job then releases every delivery of the batch. A rollback leaves no delivery, job or workflow. A reminder is its own batch, named by its delivery id; it is never deferred, so it is written `ready` and schedules no job.

A claim prevents repeated announcements across tabs/reconnects, but the winning tab can die before rendering. The card and reminder bell remain available. A revision or claim is not evidence a human saw the work. Push/email, conditional watches outside a job and a production latency SLO are not implemented.

## Evidence

[Timer runtime tests](../../apps/server/tests/timer-runtime.test.ts) use PostgreSQL, the DBOS engine and production Node: a reminder committed before the engine launches waits in the queue and fires once it does, cancelled and replaced generations never surface, and a second instance is killed while a reminder waits, its workflow claimed, adopted and fired once. [Execution runtime tests](../../apps/server/tests/execution-runtime.test.ts) use an independent SQLite-backed fault source and replay the approval's start against the finished workflow. [Watch runtime tests](../../apps/server/tests/watch-runtime.test.ts) commit two watch steps with their `jobWatch` starts before the engine launches: one is seen on its second check, the other reads three times and leaves exactly one card at its end, and a replayed start adds no second card. [Job runtime tests](../../apps/server/tests/job-runtime.test.ts) commit two nights of the sign-in clean-up before the engine launches: each runs once and completes in the ledger, one of them with a failing clean-up, and the next night waits in the engine. An instance of one release takes a night of the scan and of the clean-up from the queue and is killed; the same instance starts as the next release after the clean-up's night, its engine recovering neither, and its start takes both over, the clean-up's from a start stopped in the middle of its move and the scan's from another start that is moving it meanwhile, which leaves it: the clean-up's night runs at once and the scan's at its time, each once, and the next nights wait under the new release. [Move runtime tests](../../apps/server/tests/move-runtime.test.ts) run `scripts/workflows-move.ts` on two workflows that a killed instance of the older release left: it lists them and moves them, and each runs once under the next release from its first step without a record; it refuses a finished one, and starts an approved execution that ended in `ERROR` again from the step that failed. [Attention runtime tests](../../apps/server/tests/attention-runtime.test.ts) commit deliveries deferred by quiet hours and by the day's budget before the engine launches, and the engine runs their release jobs to make them ready. [The refresh and attention test](../../tests/db/postgres-refresh-attention.test.ts) runs the job's step over `durableJobs` on PostgreSQL and holds an admission open: the release waits on its lock, then one job releases both deliveries with `attention.released` `{ count: 2 }`. [The sign-in clean-up test](../../tests/db/sign-in-cleanup.test.ts) shows what a run removes and keeps, and that scheduling a night twice gives one job and one workflow. [The Postgres store test](../../tests/db/postgres-store.test.ts) shows the workflow row committing and rolling back with the timer intent. Memory/PostgreSQL contracts cover rollback, ownership, bounded follow-up and occurrence/attention behavior. Browser fixtures cover no-click invalidation and cross-tab claims.

The [acceptance matrix](../reference/reliability-acceptance.md) records the remaining real-source, process-death and recovery gates. Scheduled work and permission decisions do not depend on a model.
