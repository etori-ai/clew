# D97 · A new person gets one introduction card, and the help is a view built from the person's own connectors

**Status:** accepted (product owner, 2026-11-10: the plan was described and answered "Ja, börja"), built 2026-11-10 (the card with its two ways out, the help view, the row in the person dialog, the answer without a model); item 8 is a direction, not built, and its audit question is open; not compared with the design canvas, which has no artboard for it; first written as D96 and renumbered when `main` took that number the same day · **Date:** 2026-11-10 · **Area:** product, ui

**Decision.** Startsidan introduces itself once to each person, with a card in the stream and a help view that is always there. Nothing is a guided tour, and no connector ships a guide of its own.

1. **Two kinds of new, kept apart.** New to Startsidan is every person at launch and everyone provisioned later; this decision is about them. New at work (UC-OMAR-1: the checklist, the trainings, who is who) is the onboarding domain [D95](D95-clew-may-own-a-domain-by-choice-decided-with-the-core-or-connector-checklist.md) lists for a decision of its own. A provisioned person's `created_at` (D68) is when the provisioner pushed the row, not a start date, and is used for neither.

2. **New means: no introduction card yet.** The first time a person's Hem is read, the stream creates one card with the stable id `introduction:<person id>`. A card with that id in any state, open, dismissed or handled, means the person has been introduced, so the card is created once per person and never again. No column, no table and no browser storage holds the fact: the card is the record, and its audit rows (`thread.introduced`, then `thread.introduction_closed` or the ordinary `thread.dismissed`) are the history. It follows that everyone who already uses a running installation gets the card once when this is deployed, which is right: none of them has been introduced.

3. **Not from the scan.** A scanned card's identity is the occurrence per assignment (D47), so it comes back when a person changes unit or role, and a ställföreträdare's active assignment changes twice (D68 item 4). The introduction is therefore a core-owned card, written by the stream's own use case as the card of a cited answer is (D26): connector `clew`, no source authority, so it survives a change of authority and is seen as long as Startsidan's own connector is. It admits no delivery: it does not interrupt, toast or count against the attention budget (principle 6).

4. **The card, and how it leaves.** Title "Så fungerar Startsidan", one sentence, the reason "Du är ny på Startsidan. Kortet visas en gång." and one primary step, **Kom igång**, a read that opens the help beside the page. It is a requirement without a day, so it stands under Senare and is counted in Behöver dig while it is open. It does not wait for the person to find Avfärda, which is in the opened card's menu and nowhere on the row (the product owner, 2026-11-10, on trying it: "jag förstår inte hur jag avfärdar det"):

   - **Opening the help from it is the answer.** The read closes the card as handled, with the audit row `thread.introduction_closed` (reason `help-opened`, the person as actor), and answers the closed card with the text. The row keeps its place while the help is read and leaves when the help is closed; a toast says that the card is under Klart and that the help is under the person's name, and the focus goes on to the next row (2.4.3). The step's address still answers the help afterwards.
   - **Untouched, it leaves after 14 days** (`INTRODUCTION_DAYS`), at the person's next read of Hem, as dismissed, with the same audit action (reason `expired`, `assistant:introduction` as actor). A card put off with Inte nu leaves then too.
   - Avfärda still works, as on any card.

   A read closing a card is this card's rule alone: `cardDecisions` tells the stream that a card's read was answered (`answered`), and the stream closes only the person's own introduction.

5. **The help is a read with a declared text view** (`clew.help`, [D38](D38-views-are-declared-by-connectors-and-drawn-by-clew.md) kind `text`), part of Startsidan's own connector beside the search and the errand list. It opens in the context panel, which [D83](D83-interface-spaces-have-stable-navigation-roles.md) gives to reference material kept beside the task, with the address, the focus return and the phone presentation every view has. Not a tour with coach marks (Astryx ships none, and one built by hand would break the Astryx rule and is hard to make accessible) and not a wizard in a dialog (a person should be able to keep the help open while trying what it says).

6. **The frame is Startsidan's, the content is the person's.** The text has fixed sections that are the same in every installation (what the page is, the question box, the cards and their receipts, how to find the help again) and one computed section, **Det här har du**, built from the registry for the actor: every system the person can see by its `source`, each area with what it pushes and when ("Kommer hit", the manifest's `schedules`) and what can be done at any time ("Gör själv", its `standing`), the calendar as the area it already is, and the tools an administrator put in the menu. It is right the moment a connector is added or an audience changes, and nobody maintains it. A connector does not ship a guide, and the manifest gets no field for one now; if a connector later needs to say more, the place is a short additive field per area that this read draws, never a page of the connector's own.

7. **Always within reach.** The person dialog of the shared header (D39, D87) has a row **Hjälp** that opens the view over Hem. The read is a model tool with `modelReads: 'summary'`, so "Vad kan jag göra här?" is answered by showing the text, with or without a model, never by paraphrasing it. An administrator may also put it under Verktyg (D40).

8. **The person who comes back (direction, not built).** Hem is to compare two instants instead of labelling anyone an infrequent user: the previous visit, kept per person in a small table of its own with the latest one, written once per day and overwritten, never a history. "Sedan i går" then counts from the previous visit and says how long it was, and above a threshold a core-owned card says so with the same step. Open before it is built: whether the marker is exempt from the audit-row rule as an observation rather than a decision (one row per person and day otherwise), the threshold, and that nobody but the person may ever read it.

9. **Not here.** The feedback channel ("Tyck till") stores people's free text and gets its own decision, and the help gets a section for it then. A screen-reader pass is still owed, as for every new view.

10. **A text to read can be scrolled by keyboard.** The help was the first view in the panel with nothing to focus in it, and the panel's scrolling region could then not be reached by keyboard (2.1.1; axe `scrollable-region-focusable`). A panel frame now says `reads` for a `text` view, and the body's viewport is then Astryx's labelled `ScrollableArea`, which enters the tab order while it overflows, as the administration's dialogs already do. This holds for every connector's text view, not only the help.

Code: `apps/server/src/modules/help/` (`contracts.ts`, `domain.ts` with the text, `usecases.ts` with the person's page read from the registry, `capabilities.ts`), joined into the core connector in `apps/server/src/connectors/registry.ts`, the only file that names connectors; `introduce` in `apps/server/src/threads/usecases/cards.ts`, reached from `GET /api/threads` through `threads.arrive` in the composition; the row in `packages/site-header/src/person.tsx`, given its address by `apps/web/src/components/shell.tsx`, and on another site by the embed's `help-href` attribute; `reads` in `apps/web/src/components/panel.tsx`. Tests: `tests/unit/help.test.ts` (the text for two sets of connectors, the read through the registry, the router's match, and the card: once per person with its audit rows, done when the help is opened from it, gone after 14 days, not again after a dismissal or a changed unit, role or authority), `tests/a11y/help.spec.ts` (the card and its step, the row leaving when the help is closed, the dialog's row, 320 px).

**Why.** The function "Hjälp, introduktion och återkoppling" on the project's feature list has no specification; its sources are the workshop's B14 (a new or infrequent user must find a routine quickly) and "Min startsida, mina val". B14 is answered by the question box over the organisation's documents (D26), not by a tour, so the introduction's job is smaller: say what the page is and that the box exists, with the person's own systems as the example. "Mina val" is in Clew the scope and the audience, not a page builder (`docs/vision.md`), which is why the help is computed from the registry instead of written per page.

The card was explored on the canvas on 2026-11-03 as "first login as a welcome thread (no wizard)" and never decided. A card obeys the product's own rules: it says why it is there, it can be dismissed, and it is audited. A banner would sit on every page, and a modal would stop a person who came to do something.

The first login (D68 item 6, the binding) was considered as the trigger and dropped: it is over for everyone who already signed in, the binding has no time, and a stable card id needs neither. A table holding "introduced at" was dropped for the same reason.

A text view was chosen over a new component because everything a help view needs already exists for views: the panel, its address, the model's summary rule, the menu. The alternatives weighed for a guide per connector were ten tours for ten systems, the overflow the workshop's risk R03 warns about, and content Clew neither authors nor can check.

**Replaces.** Nothing. It settles the part of HANDOVER's open product question 6 about the first login; the first-week area in the same question is left to D95's onboarding domain.
