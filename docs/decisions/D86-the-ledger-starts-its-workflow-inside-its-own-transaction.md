# D86 · The ledger starts its durable workflow inside its own transaction; the outbox loops are retired

**Status:** accepted, implemented · **Date:** 2026-11-09 · **Area:** platform

**Decision.** Every durable intent the ledger commits starts its workflow in the same PostgreSQL transaction, through the engine's PL/pgSQL function `dbos.enqueue_workflow` on the transaction's own connection. The intent row and the workflow row commit together or roll back together; nothing is delivered afterwards and nothing polls for it. The three outbox loops of D45/D47 (timers in `composition/index.ts`, executions and watches in `composition/executions.ts`, scheduled jobs in `composition/jobs.ts`) and their delivery adapters (`dbos/timers.ts`, `dbos/executions.ts`, `threads/usecases/timer-dispatch.ts`, `modules/executions/dispatch.ts`) are gone.

- **Port.** A use case expresses the start through its store's transaction: `ThreadTx.enqueue(start)` and `ExecutionTx.enqueue(start)` take a `WorkflowStart` (`{ workflow, id, input }`, declared in each module's `model.ts`); a scheduled job's start is part of `scheduleJob` in every adapter, because the job row is idempotent by natural id and the start belongs to the insert. The pure helpers that name a workflow and its id live in the domain files: `reminderStart`/`reminderWorkflowId` in `threads/domain.ts`, `executionStart`, `watchStart`/`watchWorkflowId` in `modules/executions/domain.ts`, `jobStart` in `@clew/db/jobs`. The ids are unchanged: `<timer id>:v2:<generation>`, `execution:<id>` and `reconcile:<id>:<attempt>`, `<watch intent id>:<generation>`, `job:<id>`.
- **Adapters.** `packages/db/src/durable.ts` holds the one SQL statement (`select dbos.enqueue_workflow(workflow_name => …, queue_name => …, positional_args => array[…::json], workflow_id => …, application_name => …)`), and every Postgres store adapter that writes an intent takes a `DurableQueue` (`{ application, queue }`) from the composition root (`composition/durable.ts`: `DEFAULT_APPLICATION` and `ledgerQueue`), so what the ledger enqueues is what the engine the server launched dequeues. A runtime test passes its own engine's name. The memory adapters record the starts (`enqueued`) for the unit tests. Enqueueing is idempotent by workflow id: a replayed approval or a lost acknowledgement meets the existing row and changes nothing.
- **Runtime.** `dbos/runtime.ts` registers the application's ledger queue (`clew.ledger`: queue names are unique across the applications sharing a system database) on every launch with no concurrency limit, because a sleeping reminder would hold its slot for days. The four workflows the ledger starts this way (`durableReminder`, `approvedExecution`, `jobWatch`, `scheduledJob`) are registered with `serialization: 'portable'`; the SQL function writes their input as plain JSON. The queue runner polls about once a second; a row committed while no instance of the application runs waits in the queue until one launches, which is the recovery the outbox used to provide. `bun run db:init` now also creates or migrates the engine's schema (`DBOS.migrate`), so `dbos.enqueue_workflow` exists before the first ledger write on a new database.
- **Cancellation stays after the commit.** A cancelled timer or a replaced generation is ended with `cancelDurable` once its transaction has committed, best effort, by the thread store (`ThreadStoreOptions.cancel`, collected per transaction by `timerTx`); the generation fence covers a cancel that fails or never arrives, as before. `dbos.send_message` is not used: the reminder workflows wait with `DBOS.sleep`, not `DBOS.recv` (D85). An obligation timer's wait is cancelled the same way through the follow-up store; one scheduled from the execution projection relies on the fence alone, and its wait is at most hours.
- **Evidence columns stay.** The outbox tables and columns (`dispatch_outbox`, the delivery columns of `timer_intent`, `watch_intent` and `job`) are not dropped in this change: a migration would collide with concurrent schema work on `main` (0037 landed while this was built), and the rows remain readable evidence of what was scheduled. `watch_intent.delivered_at` is the approval's commit; `job.status` keeps `temporal` as the engine owner's name; `dispatched` and the timer delivery columns are written by nothing. An active timer is therefore `scheduled` as soon as it exists (`queued` remains in the contract type for older clients and is produced by nothing). The reliability counts (`undeliveredExecutions`, `oldestOutboxSeconds`, `queuedTimers`) now read the engine's queue: rows still `ENQUEUED` after thirty seconds mean no instance of the application is dequeuing. A later schema change may drop the columns once the rows have no readers.

**Why.** D85 chose the engine's system database to be Clew's own database for exactly this: a workflow start that is one more write in the ledger's transaction. The outbox was Temporal's necessity, not Clew's design: three loops, three lease tables, retry with backoff and a "queued" state in the product, all to bridge a commit and a start that can now be one commit. The spike measured 1.8 ms median for intent and start together, and the durability lane proves the same with Clew's own stores: a reminder, an approved execution, a watch step and a scheduled job each reach their workflow with no polling loop, a rollback after the intent write leaves no workflow row (`tests/db/postgres-store.test.ts`), and rows committed before the engine launches are dequeued once it does.

**Replaces.** D85's "Not done here" item (this is that step) and the outbox sentences of D45 and D47, which now read as history: approval, audit, card projection and the workflow start commit in one physical transaction, and the engine, not an outbox, carries the start. The three loops' retry-with-backoff and the `queued` timer state are gone.
