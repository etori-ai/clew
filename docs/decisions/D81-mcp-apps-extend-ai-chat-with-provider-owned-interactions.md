# D81 · MCP Apps extend AI chat with provider-owned interactions

**Status:** withdrawn 2026-11-11 (product owner: consuming a vendor's own MCP server is not a use case now; the prototype showed that the lane fits the architecture and can be built, and was then removed from the code, see [the closing note](../reviews/2026-11-11-external-mcp-chat-services-exploration.md)); was accepted direction, prototype only · **Date:** 2026-11-08 · **Area:** integrations

**Decision.** Add a second integration lane for administrator-approved MCP servers in AI-enabled conversations. A provider need not implement Clew's connector protocol. Discover its existing MCP tools and, when advertised, consume its MCP Apps resources. Clew owns discovery, access, the conversation, confirmation and receipts; the provider owns the interaction inside its isolated app.

Native connectors and Clew-rendered semantic views remain the path for model-independent work, scans, jobs across systems and Clew's durable action semantics. MCP services do not automatically become native capabilities, menu pages, scans or job steps. A service can have both lanes when that is useful.

**Why.** The product owner wants a way in for specialist interactions that do not fit the view catalogue, without asking major vendors to build a Clew integration. Expanding a universal view schema until it represents every application is not Clew's purpose. Employee satisfaction polls are a useful first example. Importance and sensitivity do not determine the lane: the distinction is a self-contained provider interaction versus work Clew must coordinate durably.

**Boundaries.**

- Available only with an authorized model in an AI-enabled conversation. This is a Clew product policy, not a limitation of MCP Apps. Deterministic app buttons do not need a model round trip. Enforcement must live in the server, including resource reads, bridge requests and background delivery.
- An administrator admits a server, audience, authentication mode and tools; the person enables a service for this conversation. Discovery does not authorize invocation. Provider descriptions, icons, annotations, resources and HTML are untrusted.
- Render the provider resource with the MCP Apps bridge and isolated sandbox. Never inject provider markup into Clew's DOM. The host chrome identifies the provider and offers close, failure and fallback states. A standard browser host needs a separate-origin sandbox proxy, constrained CSP and mediated messages.
- The model can read or propose; it cannot execute writes. App-originated writes also pass a Clew-controlled human confirmation with the target and immutable arguments bound to the decision. App visibility is not authority. Unknown effects are not retried automatically; a generic MCP tool does not promise idempotency, read-back or undo.
- Proactive delivery starts with optional administrator-configured read watches using the existing Temporal machinery: approved tool, arguments, interval, change/eligibility rule and destination. Poll invitations and tool-only outage updates exercise the same idea. An interval controls checks, not repeated notifications. Vendor-initiated push and resource subscriptions can wait. Persist/deduplicate invitations and respect audience, current authority, expiry and attention policy. Background delivery requires usable provider authorization without a live browser.
- OAuth remains a first-class requirement: standard MCP authorization, provider discovery, authorization code/PKCE, supported client registration or administrator-provided client credentials, individual login and encrypted server-side tokens. Existing vendor services must work without a Clew manifest. Local governance/watch configuration is host policy, never a new provider contract.
- Keep answers out of the model context by default. The host handles submission arguments transiently; audit/receipts should retain minimum metadata. Provider anonymity and retention claims require verification; Clew must not invent them.
- Accessibility is an admission requirement for real apps, with an accessible provider alternative where needed. A sandbox cannot repair an inaccessible UI or make arbitrary provider content conformant.

**UI exception.** Astryx has no MCP App host. The prototype may use a native iframe and a small protocol bridge; its outer UI uses Astryx. The synthetic provider's HTML/CSS is a vendor artifact, not a second Clew component system. The preview loads HTML from explicitly registered synthetic MCP providers into an opaque-origin sandbox proxy; it is not an approved production sandbox for arbitrary URLs.

**Changes to previous decisions.** D4's wrapper requirement and D38's rejection of provider HTML still govern the native connector lane. This decision adds a narrowly scoped exception for AI chat; it does not replace native views. D9's original app-host idea returns only within this boundary. No change is made to model-independent operation or to the authority required for actions.

**Build enforcement.** The MCP host is platform code beside the native connector gateway. D25 dependency/purity checks cover its use cases, and dependency rules forbid importing provider fixtures into `apps/` or `packages/`; only the independent HTTP services and tests consume those fixtures.

**Card presentation, amended 2026-11-09.** Every delivered poll invitation or service update is a separate Clew card, using the existing Astryx work-card surface, source/time line and prominent opening action. Home places these with the work below the composer. The service catalogue is an index; [D83](D83-interface-spaces-have-stable-navigation-roles.md) places it in an overlay over the current page, with a service opened above it and close returning through that hierarchy. Opening a card shows only that item's provider App or notice in the existing overlay sidebar (Astryx Drawer), or a tall BottomSheet on a phone, matching other card interactions. Home or the catalogue stays beneath the overlay with its filters and context preserved. Each delivery has its own address through `open-service`/`open-delivery`; old page links remain valid through a redirect. Close and Escape return to the opening control, browser history follows the selection, and source writes still require a separate human confirmation above the overlay. When the provider's current item no longer matches the delivery's configured identity, retain the delivered notice and offer the latest source state separately; never embed the next poll inside an older invitation. This is host presentation over standard MCP results, not a new provider manifest or view contract.

**Attention lifecycle, amended 2026-11-09.** A delivery leaves active attention when an authorized read of its source identity no longer satisfies the administrator-configured eligibility condition. Reconcile after successful human-confirmed writes, on view reads and on scheduled checks, even when the identity has not changed. Keep the source receipt and delivery history, audit resolution transactionally and preserve old links and deduplication. Do not infer completion from provider HTML, a successful mutation alone, missing fields or failed reads. The open view stays available; when removal leaves no opening control, close returns to the service section. No provider-specific tool names or extra provider contract are required. Generic notices without a condition still need an explicit acknowledgment/expiry policy.

**Implementation boundary.** The development slice uses Hillevi's real local login, database registrations and server-side actor/model gates. Independent poll/status mocks supply standard MCP over HTTP, consumed through the official SDK. Temporal runs configured reads; source identity and eligibility produce persistent, audited, deduplicated inbox entries. The home links to the generic service conversation surface; HTML is fetched from the provider only when opened. Human-confirmed writes have durable decision ids, schema validation, encrypted receipts and no automatic retry of unknown outcomes. No provider imports or name checks exist in the product UI. Vendor OAuth, production watch policy/attention/expiry, the full Apps bridge/sandbox and model tool routing/conversation opt-in are subsequent work. See [architecture](../reviews/2026-11-11-external-mcp-chat-services-exploration.md).
