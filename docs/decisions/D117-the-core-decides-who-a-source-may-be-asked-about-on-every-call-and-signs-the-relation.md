# D117 · The core decides who a source may be asked about, on every call, and signs the relation

**Status:** provisional (built 2026-11-12 on branch `about-relation` against the product owner's rule "a user can view and edit their own data and nothing else; a manager their employees'", revised the same day after an independent review; accepted once a connector outside the repository has been called under it and reads the relation) · **Date:** 2026-11-12 · **Area:** integrations, identity

**Decision.** "Who may be asked about" ([D97](D97-a-source-says-what-its-rows-are-about-and-clew-places-them.md) item 8) is one rule in the core, applied by the registry to every call that names a person or a unit, whatever path the call came by. A capability says which relations it admits, and the source is told how the caller stands to each key it is sent, in a request the assertion is bound to.

1. **Where.** `Registry.run`, `Registry.validate` before a write is approved and `Registry.document` for a document's bytes resolve how the caller stands to every key the input names before the connector is called, through the port the registry is built with (`RegistryOptions.relations`, [packages/connectors/src/index.ts](../../packages/connectors/src/index.ts)). Every way to a connector passes there: `/api/cap` and every other caller of `runCapability` (a card's action, an assistant tool, a job's follower, a document read, an effect read), `/api/connectors/call`, an in-process `clew.call` (the composites `clew.commitments`, `clew.errands`, `clew.news`, `clew.search` among them), the entities module's reads and an approved write's dispatch. The rule is the entities module's: [relations.ts](../../apps/server/src/modules/entities/relations.ts) over the people directory, with `personRelation` and `unitRelation` shared with the opened entity and its `reader` port in [model.ts](../../apps/server/src/modules/entities/model.ts); [composition/relations.ts](../../apps/server/src/composition/relations.ts) pairs it with the person's current grant. A registry built without the port asks nobody about anybody, and a directory that cannot be read is an error (`RelationsUnavailableError`), never "nobody".
2. **The relations** are closed lists in `@clew/contracts`. A person: `self`; `managed`, a direct report as [D99](D99-units-form-a-tree-pushed-over-scim-and-a-manager-works-with-their-direct-reports.md) item 4 has it (placed without a manager's role on a unit the caller manages, or reporting to it from below: the managers of the nearest led units below and the people of units nobody leads in between), a co-manager of the caller's unit only when their line runs to a unit above it that the caller also leads, and never someone who manages the caller; `colleague`, any other active person of the organisation. A unit: `manages` (the caller holds a manager's role on it) and `member` (placed on it otherwise).
3. **The declaration**, in protocol 3 (item 10). `person: { param?, admits? }`: `admits` defaults to `self` and `managed`; on a capability about a person the key is where `about` says (`keys`, `about.param`); any other names in `param` the input that takes one person's key. `unit: { admits? }` on a capability about a unit, defaulting to `manages`. Three inputs name a person whether declared or not: the `person` of a `<id>.commitments` read (the profile fixes it, D96 item 8), a property a row of a read about a person fills from its `key` when it opens another read, and an execute's effect read, which takes the execute's input and admits what the execute admits. The loader refuses a manifest in which any such input, declared or not, is not a plain string property (listed under `properties` with `type: "string"`, in an object schema without `allOf`, `anyOf`, `oneOf` or `patternProperties`), and the registry checks the input whether or not the schema lists it, so a forgotten declaration fails closed. Only Clew's own connectors may add `person.ids`: a person without a user name may then be named by Clew's id, as the talks and competence domains name them, only as the caller themself or a report.
4. **What happens to a key.** A key in `keys` the caller may not ask about is left out of the call, as are a key the directory does not know and a second spelling of one person; a key that stays is written as the directory spells it. A single key outside what the capability admits, or anything but a string where a key is named, refuses the call as an unknown capability is refused, so the answer is the same for nobody and for somebody out of reach. A call without the key passes unchanged.
5. **The source is told, and the request is bound.** In process, `clew.about`. Remote, `about` in the request body (`{ entity, relations: { <key>: <relation> } }`, `CallAbout` in the published schema), beside `actor` and `input`, never in the callback grant. Every request assertion now carries `body`, the SHA-256 of the exact request body (base64url), and on `/clew/capabilities/{name}` `capability`, that name ([D44](D44-authorized-reads-and-clew-signed-connector-authority.md), amended). The verifier every connector in the repository carries (`connectors/*/verification.mjs`, identical copies) recomputes both from the request it received and refuses any other, so the input and the relations are Clew's and an assertion cannot be replayed with another body or on another capability. The bearer stays one size however many keys a call names. A connector may answer `self` differently from `managed` without its own copy of the organisation.
6. **The connectors in the repository** declare what each did already (checked against their code, see "Why"): `hr.person`, `hr.prepareAbsence`, `appraisals.person`, `talks.person` and `competence.person` admit `managed`; `appraisals.commitments`, `competence.holdings` and `clew.commitments` take `person` and admit `self` and `managed`; `talks.commitments` takes `person` and admits `managed`; `talks.commitments`, `clew.commitments` and `competence.holdings` take ids; `qlik.unit` and `talks.unit` admit `manages`. Each still narrows by itself; nothing of that is removed here.
7. **The opened entity** does not ask a section's source about a relation it does not admit and answers "no row", which the page already leaves out, and offers only the actions that admit how the reader stands to the entity; the list does not ask a source that admits no report. Personal still lists everyone placed on the units the reader manages; the sources are asked only about the reports among them.
8. **Approved writes** ([D45](D45-approved-intent-precedes-source-dispatch.md)). Whom a payload names is resolved for an approval and for a dispatch, a new effect, and not for reading what was decided: an execution, a job and what is left to undo stay readable when the subject has since moved away from the person. Whom the payload names is resolved once per dispatch, in the check before the dispatch is recorded, and the send redeems that resolution (`Resolution`, single use, for the same actor, capability and input only), so the directory is never read between `execution.dispatched` and the send. A subject out of reach at dispatch settles the write unsent as `authority-revoked`; a directory that cannot be read settles it unsent as `source-unavailable`, as a source that cannot be reached does, and a watch's check that cannot resolve its subject is a check that did not happen.
9. **`connector-check`** says what each capability that names a person or a unit admits and warns when it declares nothing; with `--as` it sends `--keys` through the installation's own rule, without `--as` it vouches for no key at all, and it probes an unknown key and another unit past the rule and without a relation, which a source must answer as no row.

10. **Protocol 3, a break.** Three things a connector outside the repository can depend on change, so by [D60](D60-the-instance-serves-its-connector-protocol.md) item 4 this is a new number: `CallRequest` and `DocumentReadRequest` are closed objects and gained `about`, so a connector that validates request bodies against the schema of 2 refuses every call that names someone; the verifier of 3 refuses an assertion without its `body` claim, so a connector built from it answers 401 to a Clew that speaks only 2; and the loader refuses a manifest on 3 in which an input that names someone, the `person` of a `<id>.commitments` read included, is not a plain string property. `PROTOCOL_VERSION` is 3 and `PROTOCOL_ACCEPTED` is 3 and 2; the manifest's `protocol` is a union of the two; the served documents carry `x-clew-protocol.deprecated` with what a connector on 2 must change; `protocolTerms` in `packages/connectors/src/protocol.ts` is the one place the differences live. A connector on 2 is loaded and works for a window that closes by a decision of its own, no earlier than the first release after 2026-11-12: the core rule holds for it as for any connector, but it is sent no `about`, the plain-string rule is not a refusal for it (the registry still refuses anything but a string where a person is named, at every call), and it shows as "Följer ett äldre protokoll" (health `protocol-outdated`) in Administration › Anslutna system and as a warning in the conformance check. To move to 3 a connector declares `"protocol": 3`, validates against the schema of 3, verifies the `body` and `capability` claims (the verifier of 3, handed the request), and makes every input that names a person a plain string property. Every connector in this repository declares 3 and carries the verifier of 3.

**A caller with no person behind it.** D108 item 9's scheduled copy of `<id>.holdings` reads a source with nobody signed in. It is a read the installation makes, with no actor and no key in its input, so nothing in it is resolved; what it brings back is shown under Clew's own rules. If such a read ever had to name people, the port would need an answer for a system caller, decided then. Amended 2026-11-12 by [D119](D119-the-installation-reads-as-itself-through-a-read-no-person-can-reach.md): the read is declared under the manifest's `installation`, kept apart from capabilities so that no person's path reaches it, posted to `/clew/installation/{name}` with an assertion that carries no actor (subject `clew:installation`, `caller: "installation"`) and is bound to its body and name as item 5 binds every request, and answered by `connectors/moodle`. The copy that reads it is D108's, built the same day.

**Amended 2026-11-13: a unit below is a third relation.** When this branch met `main`, the record of the same number [D117, a manager follows up the units below](D117-a-manager-follows-up-the-units-below-and-a-source-is-told-them.md) had opened a unit led by a manager who reports to the reader, one level down D99's line, as the unit's page with the relation `below`, on Dialogstöd's overview, and to the sources it reads. Under item 2 such a unit had no relation, so the registry would have left it out of every call. The closed list gains `below` (`UNIT_RELATIONS` in `@clew/contracts`), resolved by the same rule (`unitRelation` in the entities module's domain, through `belowUnit`), and sent in `about` like the others; the default stays `manages`. `qlik.unit`, `qlik.economyUnit`, `qlik.hmeUnit` and `dialogue.unit` admit `manages` and `below`, which is what they answer; `talks.unit` stays `manages`, since the talks round counts only the units the reader manages. The actor's `units` of that record still travel in the signed actor beside `about`.

**Why.** An independent review, confirmed before the build, found that `GET /api/cap/<name>?input={"keys":[…]}`, the callback route and the read a section's row opens let the caller choose the keys freely, and that the entities rule let a colleague's key through to every source; every connector kept its own copy of the organisation, and one that trusted Clew would have answered across it. A second review of the first build found `managed` wider than D99 (everyone placed on a managed unit, co-managers included), inferred inputs that a non-string or an unlisted property slipped past, one unit relation for managing and belonging, a relation map in the bearer that outgrew a proxy's header limit at about 85 e-mail-shaped keys and was not bound to its call, and writes settled as revoked when the directory only could not be read; this record is the build after those fixes.

The declarations were checked against what each source answered before. The HR, appraisals, talks and competence reads about a person are for managers only, so an employee opening a colleague never saw them; the HR system answers the employees of the manager's own unit, which never lists the manager, and so does the appraisals system by its manager of record; `qlik.unit` and `talks.unit` answer only for units the caller manages. Talks and competence count as a manager's people everyone Personal lists, co-managers included: the core now leaves a co-manager out of what they are asked, which is narrower than their own check.

Alternatives weighed for the protocol: keeping the number by sending `about` only to a capability that declares `person` or `unit`, accepting an assertion without `body`, and warning instead of refusing a loose named input. That would have kept 2 for a connector that never opts in, but D60 makes a changed wire shape and a stricter loader a break, and the review asked that the binding and the plain-string rule bind; a window for 2 is the price D60 sets. Alternatives weighed for the rule. Each connector narrows by itself, as before: every connector needs the organisation, and one mistake leaks; it stays as defence in depth. The core filters but does not tell: a source cannot tell `self` from `managed` without its own copy of the directory. One relation per call instead of one per key: a batch mixes the caller with their reports. The relations in the bearer: a header past 8 KB at a proxy with long keys, and a token not bound to its input; the core splitting a batch to keep the bearer small instead: it would still leave the input unbound. Refusing a batch that holds a key out of reach: tells the caller who exists.

**Not established.** No connector outside the repository has been called under the rule or verifies the binding, and none has moved from 2 to 3; a connector with its own verifier that does not check `body` still trusts an unbound body. One connector in the repository reads `about` and answers only the keys it vouches for: `connectors/moodle`, checked against the development Moodle on 2026-11-12; the others still narrow by themselves. The cost of resolving, one read of where the caller stands per call that names someone (the tree read once, and one read of the people on each unit on the way up to the nearest led one) and one directory lookup per key for a read that admits `colleague`, is not measured. A colleague named by Clew's id is not resolved (the directory finds people by user name). Clew's own domain routes (`/api/talks`, `/api/competence`, `/api/staff`) are not capability calls and keep their own D99 check, which counts co-managers as a manager's people. On a colleague's page "Registrera frånvaro" is no longer offered (the HR system refused it there before); on Personal a co-manager's row gets no source's column or mark, and the talk drawer reads no action points for a co-manager. An input that names a person inside a nested object is not found; the protocol names top-level properties only. A key Clew does not know in another source's terms (`hr:emp:…`, a phone book's own ref, a Qlik unit ref) is that source's to narrow.

**Replaces.** Amends D97 item 8 and its "As built" item 8: the registry checks the rule on every call, `managed` is D99's direct reports only, a unit has two relations, and `colleague` reaches only a capability that admits it. Amends D44: the request assertion is bound to its body and capability, and the relations travel in the bound body. Opens the first window D60 item 4 describes: protocol 3, with 2 accepted until a decision closes it.
