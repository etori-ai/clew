# D89 · An errand connector acts as the person, and the case system decides access

**Status:** accepted (product owner, 2026-11-09); the `sm` connector's two reads built on a fixture, and the list profile and `clew.errands` built the same day; the scan, a card on demand, errand search, writes and every change outside this repository not built · **Date:** 2026-11-09 · **Area:** integrations

**Decision.** Errands reach Clew as [D35](D35-errands-are-a-connector-profile-and-a-card-is-one-systems.md) describes (one connector per case system, a shared shape for the reads, each system's own executes), with the identity and the row settled as follows.

1. **The person's own token, all the way.** An errand connector declares `delegation` (D26). Clew trades the person's session for an identity provider token bound to the case system's audience (RFC 8693) and sends it beside its assertion; the connector forwards that token to the case system and nothing else. No service credential, no asserted identity header. The audience is the installation's and is part of the manifest the connector serves.

2. **Access is the case system's.** Clew and the connector hold no group, namespace, role or access list for errands, and no mapping from a Clew person to an account in the case system. The connector asks a question that starts from the person ("my errands"), and the case system answers for everything that person may see. An errand the person may not see is not found. A namespace or business area reaches Clew only as a label.

3. **The errand row** is D35's `ErrandRow` with two additions: `state`, one of `new`, `active`, `waiting-on-me`, `waiting-on-others`, `closed`, so that lists from several systems can be ordered together, and `area`, the label of item 2. `status` remains the system's own display text and `dueAt` stays optional. The connector derives `state` from the system's status and the person's relation to the errand; what a status means is the connector's configuration. Everything else about an errand is the connector's own declared view (D38), so a field only one system has never enters the shared shape. What the person may do arrives with the card's actions, which the connector fills from what the case system allows that person on that errand.

4. **What Clew keeps** is the card: the ref, the non-personal label, the state and the person's own choices about it, with the authority that produced it (D75). Free text is read live. When the case system stops returning an errand, a complete scan resolves its card (the existing occurrence lifecycle).

5. **Reads happen while the person is signed in.** A scan for errands runs with the person's token when they open Startsidan, not at night. There is no service-credential fallback. When Clew is to tell a person about an errand while they are away, the case system sends a payload-free change event ([D19](D19-change-notification-is-a-clew-owned-contract.md)) and Clew reads when the person returns.

6. **The first connector is `connectors/supportmanagement`, id `sm`.** `sm.errands` (a list, `view: assigned | reported`) and `sm.errand` (one errand with its free text, never a tool), no area and no menu row of its own (item 8), `scan: false`. `errands.mjs` holds the port, the mapping and a made-up SupportManagement that applies its own access rule from the token; `supportmanagement.mjs` is the API adapter, written against the API the connector asks for. `scripts/auth-setup.ts` creates the development audience `supportmanagement`. Tests: `tests/unit/supportmanagement-connector.test.ts`.

7. **What SupportManagement, its gateway and the identity provider have to provide** is listed in [the connector's README](../../connectors/supportmanagement/README.md): accept the person's token, decide namespace access from that identity in the API, and answer `GET /{municipalityId}/errands/mine?relation=assigned|group|reported` across namespaces with `namespace` on each errand. None of it exists today.

8. **One list for every case system (built).** The product owner asked for it before a second case system exists, so that the second one lands in the same list and never beside it.
   - **The profile.** `<id>.errands` is a reserved name, as `<id>.search` is: a read that takes `{ view?: 'assigned' | 'reported' }` and answers an `ErrandsOutput`, an array of `ErrandRow`. Both are in `@clew/contracts` and in the published protocol's `$defs`. The read's view names, as its `open`, the read that shows one errand (`<id>.errand` by convention). Only the list is standardised; D35's `errandCard` and errand search remain to be added to the profile.
   - **`clew.errands`** is a read of Clew's core connector, in its own module `apps/server/src/modules/errands/` (contract in `@clew/contracts`, `domain.ts`, `usecases.ts`, `model.ts`, `capabilities.ts`). It asks every `<id>.errands` in the person's scope at the same time through the registry handle, so each system's scope and the person's delegated token apply; a budget per system (4 s) inside a budget for the whole (5 s). An answer that is not errand rows counts as no answer, so a connector cannot put free text in the list. The rows are ordered by state (`waiting-on-me`, `new`, `active`, `waiting-on-others`, `closed`), then the nearest `dueAt`, then the oldest `since`, each marked with its connector and the system's name and carrying the view that opens it in that system. The systems that did not answer are named (`unanswered`); when none answers the read fails, so an empty list always means no errands.
   - **Offered only with a case system.** The capability's scope is "the person has at least one errand source", so without one there is no list and no menu row, and the area is withheld by the same test (`AreaDefinition.offered`, which only a connector in Clew's own process can declare). `Registry.errandSources` tests the name before the scope for that reason. `connectors/registry.ts` joins the errand part and the composite search into the one core connector; neither module imports the other (D20).
   - **One of each for the person.** The area "Ärenden" with the list as its standing action and the menu hint "Mina ärenden" belong to `clew.errands`, and an errand connector declares neither. The model is offered `clew.errands` and not the per-connector lists (`Registry.tools`), with `modelReads: 'summary'`.
   - **A row opens in its own system.** A declared view's row could only open a read of the same connector (D38). For a view of Clew's own connectors the registry now sets `rowViews` on the view it hands the browser, and `DeclaredView` then lets a row open the `view` it carries and names the systems in `unanswered` under the rows. A connector outside Clew never gets the flag, so its rows still open only its own reads.
   - Tests: `tests/unit/errands.test.ts` (the order, a failing and a late system, a broken answer, scope, the model's tools, the SupportManagement connector as one system among others with and without the person's token) and two cases in `tests/a11y/views.spec.ts` (links into each system, the missing system named, keyboard, 320 px).

Not built in Clew: a scan that carries a delegated token (`threads/usecases/refresh.ts` runs on `systemContext`, which has no session; `docs/architecture/identity.md`), the handling of a connector `propose` that answers a `ThreadDraft`, `sm.search` with `kinds: ['case']`, and writes. A write needs two things beyond D35: text the person types has to be part of the approved input (today a card decision's input is the action's fixed input and the selected refs, `threads/usecases/decisions.ts`), and a durable execution on a delegating connector has to obtain the person's token at dispatch (today it rests at `needs-session`, `modules/executions/usecases.ts`).

**Why.** The product owner asked for errands from several systems on Startsidan, loosely coupled, and then set the constraint (2026-11-09): a general model for an errand, Clew does not keep track of which errands a person may see, and the surrounding systems may be changed to get the best result.

How SupportManagement is reached today was read from its case officers' web application (`web-app-draken-public` at `2cb2239e`): the person logs in with SAML, the backend holds one OAuth 2.0 client-credentials application for the API gateway, names the person in `X-Sent-By: type=adAccount; <account>`, and decides whether the person may use a namespace from the AD groups in the SAML answer against a list in that installation's configuration (`AUTHORIZED_GROUPS`, one installation per namespace). The access rule is therefore in a client, and any client with a gateway credential can read any namespace as any person. D18 accepted that for Clew as a known risk. Following it would have needed three things Clew does not have and should not grow: the person's AD account in the connector assertion, the person's AD groups, and a copy of the namespace-to-group rule.

The alternatives weighed, all workable against today's API: the connector looks the groups up itself (the gateway's ActiveDirectory API lists a group's members) and holds a namespace-to-group table; one connector registration per namespace with Clew's audience standing in for the group; or Clew carries the groups from the identity provider in its assertion. Each puts the rule in one more place, keeps the asserted identity, and makes Clew or its connector the thing that must be right about who sees a citizen's errand. With the rule in the case system, every client gets the same answer, a removed permission takes effect at the source, and Clew stays what the vision says it is: not a case system.

The cost is item 5. It is accepted because a card is only seen on Startsidan, where the person is signed in, and Clew sends nothing outside the application today (`docs/reference/status.md`, Browser updates). A service credential kept only for a nightly scan was rejected: it would bring back the asserted identity for the one path nobody watches.

`state` is added because five case systems have five status vocabularies, and "what waits on me" is the question the start page asks; without a shared value the composite of D35 item 4 could only order by time. The connector is built before the profile is in the protocol because a single case system needs nothing the protocol lacks: two reads with declared views.

**Replaces.** In [D18](D18-errands-are-a-clew-owned-passthrough-domain.md): the identity paragraph (a service credential with an asserted `X-Sent-By`, Clew's scope rule narrowing calls to the person's account, group and namespaces, the AD account as the first column of an identity mapping table). In D35: item 1's sentence that `sm` asserts the person with `X-Sent-By` behind its gateway credential, and item 5's push from a nightly scan for errands; `ErrandRow` gains `state` and `area`. D35's other items stand, and so do D18's rules on non-personal card text and free text read live.
