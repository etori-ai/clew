# Operations handover for SCIM, people and the organisation

Reviewed on 2026-11-11 against the published operations guide at commit `60c4203`, its companion implementation guide, the SCIM routes, the people module, the PostgreSQL adapter, OIDC sign-in and the example provisioner. [Published guide](https://etori-ai.github.io/clew/guides/provisioning-for-operations.html) · [Guide at the reviewed revision](https://github.com/etori-ai/clew/blob/60c42039ca5fcbb161fc3ac4c9a9c36e1c21fa31/docs/guides/provisioning-for-operations.md)

The page works well as a handover for planning a pilot. Assigning each deliverable to a team, using one school organisation throughout and showing the first sign-in separately from provisioning are worth keeping. Production handover needs a more precise contract for leavers, group ownership and the identity provider. The guide is candid about the evidence available so far. An installation has yet to demonstrate the whole journey with its own directory and identity provider.

## What the installation actually sends

| Concept | Value on the wire | Effect in Clew |
|---|---|---|
| Organisation | The provisioner's bearer token selects the organisation. One organisation per installation is the supported deployment. | An installation can have several root units. A root represents a branch of the unit hierarchy within the organisation. |
| Person | A `User` with a stable, never-reused source `externalId`, a unique `userName`, a name and an email address. Send `active` explicitly. | Clew returns its own SCIM `id`. The client looks up the source ID to recover that ID. First sign-in matches the configured claim to `userName` without regard to case. Subsequent sign-ins resolve the pair `iss` and `sub`. Access also requires an enabled person with a grant. |
| Department, school, team or heading in the line organisation | Each is a `Group` with `externalId=unit:<stable source unit id>` and `displayName`. A child names its parent's **group externalId** in Clew's unit extension. | One node per unit, including empty headings. Levels can differ between branches. A rename or move preserves the unit ID. Moving a branch can change which manager sees its people. |
| Placement or management | Add the person's **Clew user id** to `members` on the group at the URL containing the **Clew group id**. Use `unit:<id>` for employment and `unit-manager:<id>` for management. | The same unit with both memberships gives one manager assignment. Several placements are retained. The active assignment prefers a managed unit, then unit ID in string order. Personal reads all units the person manages. |
| Directory group or administration | A plain group can be used as an audience or explicitly mapped to a capability. A recognised `capability:<name>` group grants that capability directly. | A capability alone gives no usable session without a unit assignment. The first administrator needs both a unit assignment and `admin.users`. |

Provision the unit tree from roots to leaves, then people, then group memberships. Add new memberships before removing old ones. Delete obsolete groups after the membership changes, removing child units before their parents. The provisioner owns effective dates, change delivery and the daily reconciliation schedule. [Technical contract](../guides/writing-a-provisioner.md) · [Grant selection](../../apps/server/src/modules/people/domain.ts) · [Manager's staff view](../../apps/server/src/modules/people/usecases.ts)

For Sundsvall specifically, the product owner has already confirmed that Metakatalogen can supply a separate list of units. The pilot should use that list and establish which ID survives a reorganisation, where a manager is placed, how a replacement or second assignment is represented, and which rows remain after employment ends. Eligibility for sign-in and the handling of people with protected identities still need an explicit decision. ## Findings that affect the first installation

### High · A copied provisioner can leave leavers active or reactivate them

The guide uses `e-1001` and tells the directory team to replace the reader and keep the rest. The example entry point explicitly passes `dev:`. The reconciliation considers an absent person a leaver only when their existing ID starts with that prefix. A source using the published IDs can create everyone successfully and then miss deactivations. Group trimming may separately remove access, so checking only whether the person can sign in can miss the incorrect `active` state.

There is a second, independent path. The example's person type has no active flag and every user body contains `active: true`. If HR retains an inactive employee in its export, reconciliation sends a full replacement that can undo an earlier deactivation. Make the source's ownership and lifecycle explicit at the entry point. Test both a person missing from a complete export and a person still present with inactive status, through a second reconciliation. [Directory person](../../scripts/provisioner/directory.ts) · [Entry point](../../scripts/provisioner/index.ts) · [User mapping and leaver selection](../../scripts/provisioner/push.ts)

### High · The deletion guard and group ownership are narrower than the guide suggests

The guide says the example stops when more than a fifth would be deactivated. For a nonempty export the actual test also requires **more than ten** missing active people owned by the provisioner. Losing two people out of three passes. Even the empty-export check depends on there being at least one active person in the configured ID space.

Group cleanup has a different boundary. The example treats every `unit:`, `unit-manager:`, `capability:` and `ad:` group in the token's organisation as its own. A truncated group export can remove groups while the person count looks healthy. Two independently run writers within one organisation can also trim each other's memberships or remove groups. Make the single authoritative writer or the exact ownership partition explicit, and check completeness of the unit and group export before destructive reconciliation. A separate token for the check distinguishes its last-seen time. It still has the organisation's provisioning write permissions. [Reconciliation and thresholds](../../scripts/provisioner/push.ts) · [SCIM authentication and writes](../../apps/server/src/routes/scim.ts)

### High · Concurrent updates to one user can lose a change

The companion guide says requests touching the same person queue. Group PATCH reads its group under a lock. User PATCH reads the current person without a row lock, applies the patch to that snapshot and writes the full set of user fields. The lock taken during grant derivation comes after the user update. Overlapping changes to different attributes can overwrite one another, including the active state. This is a finding from static inspection of the PostgreSQL path. The existing concurrency suite exercises group writes and grant derivation.

Take the person lock before reading the state to be changed and cover independent person updates with a PostgreSQL contract test. The source also needs an ordering rule for its change stream and its daily snapshot. A late snapshot can overwrite a newer event even when individual server requests are correctly serialised. [User PATCH and write](../../apps/server/src/modules/people/usecases.ts) · [PostgreSQL reads and writes](../../apps/server/src/modules/people/adapters/postgres.ts) · [Existing concurrency coverage](../../tests/db/postgres-scim-concurrency.test.ts)

### High for a direct Entra integration · The OIDC handover omits a required token

The guide correctly lists `openid profile email` as the scopes Clew requests. The implementation also requires a refresh token to open the session. Microsoft's v2 identity platform requires the client to request `offline_access` explicitly to receive one. Following the guide can therefore leave correctly provisioned users unable to sign in with a direct Entra v2 configuration. Confirm the target provider's token response before handover, support its required scope in Clew and test refresh and back-channel logout as well as the first callback. Clew verifies back-channel logout tokens with RS256. [OIDC request, token checks and logout](../../apps/server/src/auth.ts) · [Microsoft's refresh-token scope](https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc#the-offline_access-scope)

### Medium · A source's department and manager need an explicit mapping

The phrase “standard SCIM 2.0” needs a short Clew profile beside it. SCIM defines users, groups, memberships and an extension mechanism. Its Enterprise User extension also defines `department`, `division`, `organization` and `manager`. Sending those user attributes to Clew can succeed while creating no placement or reporting relationship. Clew expects the unit groups and parent extension shown above. It accepts people as group members and refuses nested groups. State these facts before asking an integrator to choose a stock connector.

Write out the reporting result for the school's example. Omar sees Lena in Personal. Anna sees Omar. An intermediate unit without an active manager passes the reporting line upward. Two managers on the same unit share the unit's staff, and the source cannot express who reports to which of them using that membership alone. A matrix or individual reporting line needs a decision by the source owner. Likewise an acting-manager membership coexists with the incumbent's until the source removes it. [Enterprise user and group schemas](https://www.rfc-editor.org/rfc/rfc7643.html#section-4.3) · [Reporting behaviour and tests](../../tests/unit/organisation-tree.test.ts) · [Shared management decision](../decisions/D99-units-form-a-tree-pushed-over-scim-and-a-manager-works-with-their-direct-reports.md)

### Medium · Several accepted requests have surprising lifecycle effects

- A user `DELETE` leaves the person readable, searchable and holding their username with `active=false`. RFC 7644 permits internal retention but requires a subsequent 404 and omission from searches. Document this observable departure on the operations page. Use an explicit `active=false` for a leaver. A full user `PUT` that omits `active` sets it to true. [RFC 7644 §3.6](https://www.rfc-editor.org/rfc/rfc7644.html#section-3.6) · [SCIM user contract tests](../../tests/unit/scim.test.ts)
- Deactivation alone leaves the person's memberships and identity binding in place. When a person returns, any remaining memberships can give them their old role again once enabled. Describe how the source removes expired duties and verifies new ones before a rehire is enabled. [User updates and grant derivation](../../apps/server/src/modules/people/usecases.ts) · [Enabled-person check](../../packages/db/src/auth.ts)
- For a unit move the PATCH path is `urn:clew:params:scim:schemas:extension:unit:2.0:Group:parent`. A bare `parent` is ignored and can still produce a successful response. A full group `PUT` that omits the extension makes the unit a root, and omitting `members` empties the group. Show one move and a read-back of the parent and membership. [Parent and membership parsing](../../apps/server/src/modules/people/domain.ts) · [Unit move tests](../../tests/unit/organisation-tree.test.ts)
- The guide's error table promises a 400 for a person without a work address. Clew chooses the work address, otherwise the primary address, otherwise the first. It returns the chosen value as `type: "work"`. An export containing only a home address can therefore place a private address in Clew's work-address field. Require the source to select an approved work address or enforce that rule when accepting the user. [Email selection and SCIM response](../../apps/server/src/modules/people/domain.ts)

## Changes that would make the guide easier to operate

1. **Make the seven steps reproducible.** On an empty instance they create Anna, two units, one manager group and one capability group. The displayed result needs three users, four units and seven groups. The text qualifies it with “the whole example”, but provides no command that loads the rest. Supply the missing fixture or show the output for the steps printed. Capture returned IDs in shell variables, show HTTP failures and status codes, and replace shell placeholders such as `export KEY=<the key>` and unquoted `<id of unit:110>`.
2. **Give recovery instructions by outcome.** A 400 naming a bad attribute requires a mapping correction. A 401 needs a credential check. On an ambiguous POST timeout, look up the resource by its stable `externalId` before creating it again. Respect `Retry-After` on 503. The example client throws on errors and currently drops response headers. Add “last successful complete comparison” and “oldest unapplied change” to the provisioner's operating criteria. The timestamp in Clew records a call and can advance on a run that subsequently fails. [Example client](../../scripts/provisioner/client.ts) · [Last-seen accounting](../../apps/server/src/modules/people/usecases.ts)
3. **Explain what success looks like.** On an unchanged source, the example still sends a `PUT` for every present person. The useful invariant is unchanged identity, membership and grant state. The checker exits zero even with warnings and `--roots` warns only for excess roots. It does not compare the full topology or verify each intended manager or administrator. Include source-to-Clew checks of exact parentage, expected placements and named people who should gain or lose access. [Checker](../../scripts/provisioner/check.ts) · [CLI exit status](../../scripts/provisioner-check.ts)
4. **Correct sign-in troubleshooting.** An unknown or disabled username can produce `identity-unmatched`. A changed subject for an already bound account produces `identity-conflict`. A missing binding claim can reach `login-denied` without either event. A person can also be bound before Clew establishes that they have a usable grant. Administration shows that binding, so verify the result using an actual signed-in request. On a move, removing the last assignment first ends a session if a protected request arrives during the gap. [Binding and audit](../../packages/db/src/auth.ts) · [Session checks](../../apps/server/src/auth.ts) · [Administration row](../../apps/server/src/modules/people/usecases.ts)

## Pilot acceptance

| Exercise | Evidence the directory, identity and hosting teams can agree on |
|---|---|
| Load the school example from an empty instance | Four units, the exact three parent links, three users and seven groups. Anna administers users and sees Omar in Personal. Omar sees Lena. An account present only at the IdP is denied. |
| Move Lena and move a branch | Lena's Clew ID survives. Both the old and new manager's staff lists reflect the final placements. The moved branch retains its members and shows its new parent after a read-back. |
| End and restore a placement or employment | An acting manager loses the intended reach on the effective date. A deactivated person cannot make a protected request. A subsequent full comparison preserves the intended active state for both retained and absent source rows. |
| Interrupt delivery and truncate an export | A retry of an already-created object recovers the same ID. A delayed event and a daily run converge on the newest source state. The operator can distinguish a successful comparison from a recent failed call. An incomplete group export cannot erase another source's groups. |
| Use the installation's real IdP | One provisioned, placed person can sign in, refresh the session and sign out through the back channel. A missing claim, a changed subject and a missing assignment can each be diagnosed. |

The published seven-step code blocks matched the source at the reviewed revision and their create requests were counted directly. The existing unit tests cover tree order, moves, interrupted reconciliations and grant derivation. GitHub's check and database/reliability workflows passed for this revision. A focused local test attempt encountered a missing `pino` dependency and the supervisor stopped it at 90 seconds. The concurrency finding was assessed from code. No production directory or external IdP was exercised in this review. ## Outcome

The example provisioner now requires an explicit source scope and a complete snapshot. It preserves inactive source rows, disables absent people in scope and enables a returning person after reconciling memberships. Before applying changes it checks withdrawals of users, units, plain groups and derived role groups: all of a population, or more than one row and more than a fifth of it, needs an operator's `force`. An inactive source row Clew has never held is not created, since it would hold the account name against its next owner. After a 503 the summary continues from the first attempt. The regression tests include non-development source IDs, two absent users out of three, a foreign group's membership and an interrupted rehire.

User mutations lock the organisation-scoped row before reading its fields. A PostgreSQL test overlaps deactivation and a name change and checks both the resulting person and the audit records. The OIDC client can request offline access for a direct Entra v2 integration. Work-address selection takes a `work` address or one without a type and never an address of another type, and a user with such addresses alone is told so. An unqualified parent on a unit group receives an error in a PATCH and in a body, whatever the order of the keys.

The operations walkthrough now creates the complete school example and reads back both its branch move and its leaver. A test runs the guide's Bash blocks verbatim against the SCIM routes and compares both printed outputs, all parent links, the two managers’ staff lists and Anna's administration grant. External directory data, production consent, refresh and logout with the installation's own IdP remain pilot acceptance cases.
