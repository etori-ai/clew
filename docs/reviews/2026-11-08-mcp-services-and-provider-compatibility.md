# MCP services and employee-survey provider compatibility

Reviewed 2026-11-08 from first-party public documentation. No customer account was connected, no OAuth consent granted and no authenticated tool catalogue inspected. “Not verified” means the documentation reviewed did not establish the capability; it is not proof of absence.

**Finding.** A standards-based MCP client is useful now. An MCP server, a ChatGPT directory listing and an MCP App HTML resource are different things. Clew should support ordinary tools independently from Apps, and add proactive watches without asking providers for a Clew manifest. The synthetic weekly poll illustrates the interface boundary; it must not become a vendor compatibility promise.

Additional checks:

- **15Five** has an official MCP offering. Its marketing page describes read-only review data, while newer product-release/admin documentation mentions a separate setting for updates. Treat the exact tool set as version/account dependent and inspect it rather than asserting that writes are absent. Neither establishes the proposed poll App. [MCP page](https://www.15five.com/mcp), [October release notes](https://success.15five.com/hc/en-us/articles/50989471559067-What-s-new-in-15Five-Product-releases).
- **Simployer** documents an MCP access path to its public API, but its guide says tokens currently carry unscoped owner-level rights across the tenant. That is unsuitable as a transparent employee-scoped connection in Clew. Do not assume Simployer MCP means &frankly poll participation. [Official customer guide](https://simployer.freshdesk.com/en/support/solutions/articles/201000132208-simployer-mcp-model-context-protocol-tools-customer-guide).
- **Workday Peakon:** no first-party Peakon-specific MCP poll endpoint was verified in this review. Workday's broader MCP platform announcement does not establish Peakon tool or App coverage. [Workday platform announcement](https://blog.workday.com/en-us/trusted-agent-platform.html).
- **MCP Apps in enterprise SaaS is real beyond surveys:** Oracle documents standard UI-resource metadata and bundled HTML for NetSuite custom tools. This supports the extension direction, not a claim that NetSuite supplies employee polls. [Oracle MCP Apps documentation](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/article_0324030845.html).

## Consequences for the implementation

1. Ship a generic MCP/OAuth client first; neither connection nor tool use depends on a Clew manifest, poll-specific names or an App.
2. Discover an interactive app through the negotiated standard extension and tool/resource metadata. Fall back to a tool result when no app exists. Do not relabel a provider's website iframe as an MCP App.
3. Make watches a host feature: approved read + fixed inputs + interval + a tested change/eligibility rule + destination. A provider's stable status or invitation fields determine whether this works. No background watch is inferred from merely connecting a service.
4. Validate three separate promises with an actual account: interactive tool calls, portable App rendering, and background authorization/data suitable for watches. Passing one is not passing all three.
5. Keep the prototype provider-independent and label synthetic behavior. A first pilot could exercise a well-documented custom OAuth client with Lattice or ordinary engagement reads with Workleap, then validate the respondent flow with ScatterSpoke. This is a technical validation order, not a purchasing recommendation.

The stronger demonstration is Hillevi receiving an attributed outage update from a tool-only service and opening a synthetic poll App from an invitation. The same host can consume both without owning either source's business UI.
