# Handover review of the SCIM provisioning guides

On 2026-11-13 we reviewed the two Markdown pages VitePress publishes for the directory, identity provider and hosting teams. [PR 63](https://github.com/etori-ai/clew/pull/63) · [Reviewed revision 99860c08](https://github.com/etori-ai/clew/commit/99860c08b5381343c643a7251f51a8f25a477dd8)

## Corrections before handover

1. **Coordinate both sides of an account-name handover.** The instructions cover the point at which the new account may start presenting a reused name. They also need a condition for the former holder. Before moving the name onto a different active Clew person, the IdP team must confirm the former account can no longer sign in with that claim. This matters when an account has never been bound and both people still work for the organisation. Agree a sign-in pause for the affected accounts if the directory and IdP teams cannot guarantee this ordering. Release the new account after confirming the name belongs to its intended person in Clew. The opening diagram's caption should identify name matching as first sign-in. Subsequent sign-ins look up the binding by issuer and subject and check for a conflicting claim. [Operations instructions](../guides/scim-sign-in-and-hosting.md#the-claim-and-the-user-name) · [Integrator instructions](../guides/writing-a-provisioner.md#renames-reused-names-and-sign-in) · [Sign-in and first binding](../../packages/db/src/auth.ts)

2. **Use the same return-to-work rule for events and daily reconciliation.** The event table tells the writer to add the current unit and withdraw expired duties. The departure instructions name manager, capability and plain groups for removal. An old employee placement can therefore survive a return to a different unit. Before reactivation, check the person's actual groups, confirm an intended placement, and check that every membership this writer owns is still intended. Leave the person inactive if the checks fail. Where several writers contribute, assign responsibility for confirmation across writers. The example checks its own groups. Also describe the zero-match case. A person who was already inactive at first import may never have had a Clew row. Once the source identity and absence are confirmed, follow the first-time provisioning path. [Event table](../guides/scim-directory-operations.md#what-it-sends-when-something-changes) · [Daily rule, step 8](../guides/writing-a-provisioner.md#what-a-provisioner-does-on-every-reconciliation) · [Example implementation](../../scripts/provisioner/push.ts)

3. **Make a targeted parent update the recipe for a unit move.** The organisation-tree section offers a full group `PUT` to move a unit. With a valid name and parent, omitting `members` empties its membership. People can lose their placement as a side effect of moving a node. The worked school example already shows a parent-only `PATCH` and reads back the members. Lead with that recipe and put the complete-membership requirement beside the `PUT` option. [Tree instructions](../guides/writing-a-provisioner.md#the-organisation-tree) · [Worked move](../guides/scim-directory-operations.md#what-it-sends-when-something-changes) · [Full group representation](../../apps/server/src/modules/people/domain.ts)

4. **Document explicit null on whole-list removal.** The phone and employment sections promise HTTP 400 when an unfiltered `remove` carries a value. For both lists, explicit `value: null` is treated like an omitted value and clears the whole list. A supplied non-null value is refused on an ordinary update. Show these cases side by side so a client that serializes optional fields as null can predict which data survives. [Phones](../guides/writing-a-provisioner.md#phone-numbers) · [Employments](../guides/writing-a-provisioner.md#current-employments) · [Patch implementation](../../apps/server/src/modules/people/domain.ts) · [SCIM route test](../../tests/unit/scim-as-clients-send-it.test.ts)

## What to keep

The two entry points identify who owns the source mapping, identity provider and hosting. The operations guide distinguishes event delivery, which the directory team implements, from the daily comparison supplied as an example. The school exercise connects requests to concrete placements, reporting lines and observable acceptance criteria. Preserve these examples and link to one maintained lifecycle rule when both guides need it. [Guide index](../guides/README.md) · [Directory team's deliverables](../guides/scim-directory-operations.md#the-directory-team-a-provisioner)

The create contract explains that Clew requires a stable `externalId` for a new user or group. This is a Clew requirement. SCIM defines the attribute as optional, and Okta's published Group Push creation request omits it. The technical guide correctly explains the need for an adapter in this case. A short link from the operations team's mapping checklist would put this integration decision before implementation. [Clew's create rule](../guides/writing-a-provisioner.md#how-a-request-is-read) · [RFC 7643 §3.1](https://www.rfc-editor.org/rfc/rfc7643.html#section-3.1) · [Okta Group Push](https://developer.okta.com/docs/api/openapi/okta-scim/guides/scim-20#create-groups)

## Outcome

Both guides now use the same return-to-work procedure for events and reconciliation. The directory and identity provider teams share one account-name handover procedure. The protocol guide specifies the effects of full group replacement and explicit null on whole-list removal. The smaller corrections above are in the team checklists and the relevant contract sections.
