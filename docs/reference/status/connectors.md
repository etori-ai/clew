# Implementation status: connectors in this repository

One page of [implementation status](../status.md). Each entry says what works in this checkout, what limits it or is still to do, and where the code and tests that show it are.

## Fixture connectors

**Works in this checkout.** Seven generic systems (HR, economy, deviations, communication, time reporting, payroll, an IT service desk) as independent services behind the protocol under `connectors/`, run by the development stack, registered by `bun run dev:connectors`, run in-process by the unit suites; writes deduplicated by the operation id with read-back, fault switches, id maps.

**Limits and pending work.** Fixtures, not real systems: no vendor API and no real identity mapping. HTTP process tests cover lost-response recovery, restart, undo and the HR/payroll feed. Bootstrap preserves existing governance; reset explicitly retires old work. The destructive live-stack reset is a separate operator check.

**Evidence.** [hr](../../../connectors/hr/README.md), [helper](../../../tests/fixture-connectors.ts), [HTTP proof](../../../apps/server/tests/fixture-runtime.test.ts), [reset proof](../../../tests/db/fixture-maintenance.test.ts), [D61](../../decisions/D61-fixture-sources-are-independent-connectors.md)

## Errands

**Works in this checkout.** Same-connector card action rule. The list profile `<id>.errands` (`ErrandRow` with a shared `state` and an `area` label, in the protocol's `$defs`) and the combined list `clew.errands` ([D89](../../decisions/D89-an-errand-connector-acts-as-the-person-and-the-case-system-decides-access.md)): every case system in the person's scope asked at once under a budget, the rows ordered by state across systems, each row opening in its own system, the systems that did not answer named, offered only to a person with a case system; one area, one menu hint and one model tool whatever the number of systems. `connectors/supportmanagement` (id `sm`): a person's errands (`sm.errands`, assigned or reported) and one errand in the panel (`sm.errand`, never a tool), read with the person's delegated token; a fixture that applies its own access rule from the token, and an API adapter. On Hem the combined list is a section "Mina ärenden" after the day's work for a person with a case system ([D90](../../decisions/D90-mina-arenden-is-a-section-on-hem.md)): the first five rows, the rest in place, a row opening its errand beside the page.

**Limits and pending work.** The API adapter has not met a SupportManagement: `errands/mine`, user tokens and access decided in the API are requirements on SupportManagement, its gateway and the identity provider ([connector README](../../../connectors/supportmanagement/README.md)). No scan (a scan carries no delegated token), so no errand cards on Hem. A card on demand, errand search, writes and a CaseData connector are not implemented. The section on Hem is a read, not cards: it is not counted in Behöver dig or Lugnt läge, and the design canvas has no errand section to compare it with. The `sm` connector is registered by hand, not by the development stack's bootstrap. No screen-reader pass.

**Evidence.** [D35](../../decisions/D35-errands-are-a-connector-profile-and-a-card-is-one-systems.md), [module](../../../apps/server/src/modules/errands/usecases.ts), [connector](../../../connectors/supportmanagement/connector.mjs), [unit tests](../../../tests/unit/errands.test.ts), [connector tests](../../../tests/unit/supportmanagement-connector.test.ts), [browser evidence](../../../tests/a11y/views.spec.ts), [Hem section](../../../tests/a11y/errands.spec.ts)

## Requests

**Works in this checkout.** The requests profile `<id>.requests` (`RequestRow` and `RequestsOutput` in the protocol's `$defs`: `ref`, `label`, a shared `state` of four, the system's own `status`, `since`, an optional `expectedAt` and `link`, nothing else) and the combined list `clew.requests` ([D123](../../decisions/D123-requests-are-a-profile-of-their-own-apart-from-the-errands-a-person-handles.md), provisional): what a person ordered or reported in a service desk and waits for, kept apart from the errands a person handles. Every system in the person's scope asked at once as the person under the errand list's budgets, an answer out of shape counted as no answer, the rows ordered what waits on the person first, then what is open from the oldest, then what is closed from the newest, at most 200, each opening in its own system when the person may open it, the systems that did not answer named, and a read that fails when none answers. Offered only to a person with such a system; one area, one menu hint ("Mina beställningar") and one model tool reading a summary whatever the number of systems. On Hem a section "Beställningar och felanmälningar" directly after "Mina ärenden": the first five rows with the shared state as a badge in the word `clew.requests` gives it ("Väntar på dig" in the warning tone, "Ny", "Pågår" and "Stängd" neutral; the desk's own views draw its own status instead), the systems that did not answer, and the view's "Visa allt" to the list's page `/tools/clew.requests` when there are more, with Hem as its way back; a row opens the request beside Hem. The first source is `connectors/servicedesk`, the IT service desk of the development stack (port 4054, registered and enabled by `bun run dev:connectors`): the asking person's own orders and fault reports by number and type, open ones and those closed in the last 30 days, and one request with its free text in the panel (`servicedesk.request`, the person's own only). It adds an order from the desk's catalogue for a person (`servicedesk.order`, an execute about a person in the person's menu, for oneself or a direct report, `person.admits: ['self', 'managed']`, with a choice and an optional message, its effect read, deduplicated by the operation id and read back through `servicedesk.lookup`), a waiting card per open request the person made (waiting on the desk, or the person's own work when the desk waits for them, resolved by a complete observation when the desk closes the request), and what the desk has registered to a person (`servicedesk.person`, a section on the opened person, opening `servicedesk.equipment`). A fixture-only route behind a key moves a request forward. Its records are shaped as a typical service-desk API answers, behind a source port with the fixture as the only implementation.

**Limits and pending work.** The only source is a fixture; no real service desk has answered the profile, and nothing has been seen on the development stack in a browser. The read is about the person who asks; no input asks for someone else's requests, and an order placed for someone is listed for the one who placed it, not for the person it is for. The person cannot answer the desk, confirm a delivery or withdraw an order from Clew; no search. The design canvas has no such section. No screen-reader pass.

**Evidence.** [D123](../../decisions/D123-requests-are-a-profile-of-their-own-apart-from-the-errands-a-person-handles.md), [module](../../../apps/server/src/modules/requests/usecases.ts), [capability](../../../apps/server/src/modules/requests/capabilities.ts), [unit tests](../../../tests/unit/requests.test.ts), [Hem section](../../../apps/web/src/components/my-requests.tsx), [browser evidence](../../../tests/a11y/requests.spec.ts), [fixture](../../../connectors/servicedesk/README.md), [fixture tests](../../../tests/unit/servicedesk-connector.test.ts)

## News

**Works in this checkout.** The news profile `<id>.news` (`NewsRow` and `NewsOutput` in the protocol's `$defs`: `ref`, `title`, `sender`, `publishedAt` and an optional `link`, nothing else) and the combined list `clew.news` ([D112, amended 2026-11-11](../../decisions/D112-the-interface-is-rebuilt-on-astryx-templates-a-queue-one-detail-shape-one-panel.md)): every news source in the person's scope asked at once as the person under a short budget, the rows newest first across sources, each row leaving by its link or opening in its own source by the read its view's `open` names; a source that fails, is late or answers out of shape contributes nothing and is not named. Offered only to a person with a news source; one menu hint ("Nyheter") and one model tool reading a summary whatever the number of sources; never a write. `connectors/communication` is the first source: its notices as news with their senders (`communication.news`), the routine "Ny rutin vid hot och våld" with a `link` to its full text, which leaves Clew, and the survey without one, which opens its text in Clew (`communication.newsItem`). The same fixture marks its "Jag har läst" as the read receipt (`acknowledgement: { publishedAt }` on the draft's action, refused on anything but one execute per item), which Hem lifts as Fokusnyhet; its work item is the notice (D112, amended 2026-11-12): the text of a few paragraphs as the `summary`, a `reason` naming the sender, one row with no detail, and "Läs hela nyheten" as a read with `target: 'link'` (`communication.open`, answering `{ url }`). On Hem the three newest are the block "Nyheter" and the whole list is "Alla nyheter" ([Hem under the box](interface.md#hem-under-the-box)).

**Limits and pending work.** No connector to a real news source; the fixture's news are its notices, and its one link out is a synthetic address on a reserved example domain. No feed a person can opt out of (B8). A fixture seeded before notices had a sender and a link lists the system's name as the sender and has no link until it is reseeded (`bun run fixtures:reset`, or the service's `records` removed). The unit tests pass, and on 2026-11-11 the development stack answered `clew.news` with the fixture's two notices, newest first, each opening its text through `communication.newsItem`.

**Evidence.** [module](../../../apps/server/src/modules/news/usecases.ts), [capability](../../../apps/server/src/modules/news/capabilities.ts), [fixture](../../../connectors/communication/manifest.mjs), [unit tests](../../../tests/unit/news.test.ts), [read receipt](../../../tests/unit/read-receipt.test.ts)

## Nextcloud Approval

**Works in this checkout.** `connectors/nextcloud-approval` (D101, provisional): the first connector to a product that was not written for Clew. It acts as the person with a token exchanged for the audience `nextcloud`, checks that the token's Nextcloud account is the actor Clew named, and holds no service credential. Reads: what waits for me (table) and one file's approval state (detail). A scan gives one card per waiting file; Godkänn and Avvisa are executes on the `manual` strategy whose receipt is the state read back from Nextcloud. The development Nextcloud ships `user_oidc` and `approval`, seeded by `sh scripts/calendar.sh seed`. The loop (visit, scan, card, decision, dispatch with the person's token, receipt, audit) passes on the memory adapters and has run through the same use cases against the real Nextcloud and Keycloak for two people. Signed in on the development stack on 2026-11-11, on the page: as Hillevi the visit's scan gave three cards, Godkänn and Avvisa each gave a receipt on Hem, and Nextcloud's own records and Clew's audit rows agree; as Hassan the scan gave his two files and none of hers; when his shares were removed in Nextcloud both cards left Hem at the next scan, without a reload (`work.resolved`); a decision on a file whose content had changed since the card was made is shown as "Beslutet registrerades inte i Nextcloud" with the reason on the open card (`execution.failed`), and a decision sent while the connector did not answer as "Källans besked saknas" (`execution.unknown`), the file still waiting in Nextcloud both times.

**Limits and pending work.** Of D101's conditions only the manual pass with a screen reader is left; the product owner lifted the freeze on new surface on 2026-11-12 without it, and the pass is still owed. The second build as an MCP server is no longer a condition (D101, amended 2026-11-11). Found on the page on 2026-11-11 and not fixed: a card whose decision failed or is unknown cannot be decided again or dismissed (its menu holds "Lägg till i samtalet" alone, and on a page without a question box it has no menu; any connector); Kontrollera status changes nothing on the page for a `manual` write, so a lost answer stays unknown until the person looks in Nextcloud; the outage banner says that what is sent is queued, which is not so for this connector; and access given back brings no card back until approval is requested again. Registered by hand, not by the development bootstrap. No message with a rejection; group or circle approvers, group folders and more than fifty files in one read are untried. The running calendar container must be recreated once to reach Keycloak by its compose entry.

**Evidence.** [D101](../../decisions/D101-the-first-real-integration-is-nextclouds-approval-app-and-new-surface-waits-for-it.md), [findings](../../reviews/2026-11-10-what-the-first-real-integration-showed.md), [connector](../../../connectors/nextcloud-approval/README.md), [recorded exchanges](../../../connectors/nextcloud-approval/samples/README.md), [connector tests](../../../tests/unit/nextcloud-approval-connector.test.ts), [loop test](../../../tests/unit/approval-loop.test.ts)

## Learning platform (Moodle)

**Works in this checkout.** `connectors/moodle`: Moodle LMS read through its REST web service API as one service account with a token from configuration, never the person's. `moodle.person`, a read about a person (D97), gives the opened person a section "Utbildningar" with how many courses are completed and under way; its row opens `moodle.courses`, one person's courses ("Pågår", "Genomförd" with the day) and badges ("Giltigt", "Utgånget" with the day they ran out); a course's row opens `moodle.course`, a detail with the category, the day, the completion criteria met and when, and the summary as text, and links to the course in Moodle when `MOODLE_PUBLIC_URL` is set. `moodle.holdings` answers D108 item 9's holdings profile as the installation's read ([D119](../../decisions/D119-the-installation-reads-as-itself-through-a-read-no-person-can-reach.md)): no person reaches it; Clew reads every account the service account can see, 25 to a page in Moodle's id order (the front page's participants, which needs `moodle/site:viewparticipants`), each with every completed course and badge, the source's row id and type id, the day issued and, for a badge, the day it ends; an account with nothing is a row without holdings, a withheld or ambiguous account no row, suspended accounts are answered, and every page says `withdrawalsReported: false`, since Moodle leaves holdings out without saying so. The cursor survives accounts deleted during a read, a page stops taking accounts halfway to its deadline, and the connector answers it only to the installation's own assertion (a person's is 401). A person is matched on Moodle's `username` (default) or `idnumber`, and a key matching two accounts is no one. On protocol 3 (D117): `moodle.person` (by `keys`), `moodle.courses` and `moodle.course` (by `person`) admit `self` and `managed`, and the connector answers exactly the keys the bound request's `about` vouches for under those relations, keeping no copy of the organisation; no `about`, another relation or an assertion not bound to the body is no row, not found or 401. One person or course Moodle refuses is left out of a batch and marks the row partial; a read has a deadline, and stops its calls when Clew goes away or one call fails it. Moodle's HTTP-200 errors map to `denied` (the token or the service's rights) and `unavailable`. Recorded exchanges with the development Moodle and a stand-in for the unit tests. On 2026-11-12 the conformance check passed against the development Moodle on protocol 3 with real keys through the installation's rule as Hillevi, and the reads answered live through that rule: Hillevi her eleven direct reports and herself, Hassan himself only. The same day the installation's read ran in process from the change's worktree against the development Moodle: 16 accounts in one page (Moodle's guest account left out), 50 holdings, no partial row, 81 Moodle calls, 0.4 to 0.7 s; the conformance check in process passed with the person refused on the route.

**Limits and pending work.** Registered by hand on the development stack; the section and the course detail have not been checked on a page by this work, and there has been no screen-reader pass. The competence register's copy (D108 item 9) reads it through the port `HoldingsReader`; it has run end to end in process against the development Moodle (16 accounts, 50 holdings of 14 people stored, the administrator and the service account matching nobody, outcome complete), not yet in the running server. An account whose reads take longer than the page's deadline is answered partial, empty if nothing of it was read, and the cursor moves past it. A refusal keeps its kind and Clew's words for it; the connector's own message goes nowhere further. The running compose service serves the checkout on `main`; the installation's read was checked in process, against one page of 16 accounts, not against a Moodle of thousands or one that pages. Suspended Moodle accounts are answered, and a user name Clew gives to someone new while the old account is suspended and not renamed carries that account's rows. Ended enrolments, courses the account cannot enter, private badges, switched-off course badges and accounts whose details are withheld are not seen. One Moodle call per person and completed course for a completion date. Competencies are not read. Not registered by the development bootstrap.
