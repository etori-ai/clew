# Implementation status: operations and models

One page of [implementation status](../status.md). Each entry says what works in this checkout, what limits it or is still to do, and where the code and tests that show it are.

## Observability

**Works in this checkout.** One `pino` logger on stdout (JSON, `scope`, `trace_id` on every line) behind the folders' `log` ports; `console.*` is gone from the server. With `OTEL_EXPORTER_OTLP_ENDPOINT` set, OpenTelemetry traces and metrics leave over OTLP/HTTP: a server span per request (`@hono/otel`), every outgoing `fetch`, DBOS workflows and steps on the same tracer, and the AI SDK's `gen_ai.*` spans for every model turn with content recording off. A model turn's provider, duration, steps, tokens, finish reason and trace id are in `MessageMeta.modelCall` and the turn's audit row, also when the router answered in its place, whose reason it carries; a turn that called a model, read or started a work item and then was stopped, was offered to another system's assistant or failed writes `conversation.stopped`, `conversation.offered` or `conversation.failed` with them. A turn stopped after the model's propose started a work item is not stopped there (WD-L3): it is written whole, the item its answer, as `conversation.asked` or `conversation.replied` with `stopped: true`; the stops the people pressed are the `conversation.stopped` rows and those. A turn whose question key another send wrote first is `conversation.failed`, a question handed to another system's assistant included. A failed statement is logged as its type, the statement with its placeholders, its stack frames and the database's SQLSTATE and constraint, under "Failed query", never with the values it was given: in the log line, in the error the request's span records and in the durable engine's retry warning and step span. A request span records the path without its query and with `:key` in place of an entity's key (the segment after `/api/entities/<kind>/`), and a failed request's log line names its route template (`route`), not its path. The sign-in's log lines are in [Sign-in and sessions](identity.md#sign-in-and-sessions). The development stack runs `grafana/otel-lgtm` (Grafana on 3023).

**Limits and pending work.** No spans for Clew's own `postgres.js` queries; no OTLP log export from the process (a collector reads stdout); no administration page over audit rows; Grafana in the stack is anonymous; the GenAI conventions are at Development status and may rename attributes.

## Operations

**Works in this checkout.** Authorized aggregate reliability endpoint/CLI, conservative upgrades, synthetic backup/restore rehearsal and a separate real-stack CI lane. `/api/ready` answers 503 unless startup has finished and the database answers within a second. The server empties expired sign-in data itself every night ([Sign-in and sessions](identity.md#sign-in-and-sessions)). The operator's scripts for one person run in the app container, name the person by id and are audited with the actor `operator:cli`: `identity-rebind` moves or releases a sign-in binding, and `subject-erase`, `talks-erase`, `competence-erase`, `dialogue-erase`, `boarding-erase` and, last, `person-erase` erase a leaver, in that order ([A leaver's record and its erasure](identity.md#a-leavers-record-and-its-erasure)).

**Limits and pending work.** Production thresholds, coordinated engine-state/source recovery, screen-reader verification and selected-source gates remain open.

**Evidence.** [Runbook](../../maintainers/reliability-operations.md), [operations guide](../../guides/provisioning-for-operations.md), [CI](../../../.github/workflows/reliability.yml)

## Container images

**Works in this checkout.** Two images built from the repository root ([D131](../../decisions/D131-clew-builds-a-server-image-and-a-web-image-from-the-repository-root.md)): the server (`apps/server/Dockerfile`: Node through tsx, Bun and the operator's scripts, the build argument `CLEW_RELEASE` kept as the release) and the web app (`apps/web/Dockerfile`: nginx serving the built files and passing `/api/` and `/scim/` on to `CLEW_SERVER_URL`, with `third-party-notices.txt` and `LICENSE.txt` among the files it serves, D146, and every page and file sent with the content security policy, framing rule and other headers of `apps/web/security-headers.conf`, D145). Every connector image holds `LICENSE`. `scripts/images.txt` lists them and every connector's image, and `scripts/images-build.sh` builds what it lists. On 2026-11-17 both were built with Docker and with buildah, and run on a workstation as an arbitrary user in group 0: `bun run db:init` migrated an empty PostgreSQL 18.6, the server started, launched the durable engine under the build's release and answered `/api/health` and `/api/ready`, `bun scripts/workflows-move.ts` ran, and the web image served the app, answered an unknown path with `index.html` and passed `/api/` and `/scim/` on. Since 2026-11-18 a pipeline outside the repository reads `scripts/images.txt` and builds the server, the web app and the ten connectors of the development stack, and they run on an OpenShift test cluster on made-up data, each as the user the platform gives it: the server migrated its database and started there, the web image serves the instance's address, and each of the ten connectors answers its manifest.

**Limits and pending work.** On the test cluster a sign-in went to a lab Keycloak and back on 2026-11-18 and was refused because the directory was empty; nobody is recorded as having used a page there, and the connectors are not registered in that instance. The server image holds the whole workspace with its development dependencies (about 1.4 GB), because the scripts at the root resolve their imports through the root's development dependencies. No image is published anywhere and nothing in CI builds them, so a change that breaks a Dockerfile is found by whoever builds next. Of the connectors' images, `hello`'s was built on a workstation and the ten of the development stack by the pipeline; the other seven have not been built. The finance connector's image did not start until its Dockerfile was given `documents.mjs` on 2026-11-18; every connector's Dockerfile was then compared with what its code imports, and no other lacked a file. No compose file or manifest for a whole installation is in the repository. The security headers were read from the image's nginx serving a build on a workstation on 2026-11-23, and the accessibility suite draws every page under them; they have not been looked at behind the test cluster's proxy.

## Model configuration

**Works in this checkout.** Providers/models are administered in the product and database. A provider is marked down only when its endpoint does not answer or refuses the key; a turn that runs out of its 60 seconds or that the endpoint refuses marks nothing. An address on another host removes the provider's key in the same audited change. A model's audience that names a provisioned group offers the model to its members ([Users and identity](identity.md#users-and-identity)). `scripts/models-check.ts` checks a model end to end on the development stack: it refuses to run unless `CLEW_POC=true` or `--confirm` is given, switches its throwaway model on for its own throwaway unit only and checks that a person outside that unit is not offered it, and its clean-up deletes only the audit rows whose actor is its own run's person.

**Limits and pending work.** Old `AI_*` setup instructions are obsolete. Model independence remains the product requirement. A models-check run killed before its clean-up leaves the model, its provider, their audit rows and a person in organisation `check` behind.
