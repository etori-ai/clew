# Implementation status: work, decisions and durable execution

One page of [implementation status](../status.md). Each entry says what works in this checkout, what limits it or is still to do, and where the code and tests that show it are.

## Approved writes

**Works in this checkout.** Generic card decisions and calendar create/move/cancel/confirm/undo use encrypted intent, transactional audit/card projection and workflow start (D86), read-back and linked compensation. Calendar API writes require a stable `decisionId` and return a pending card. A card decision takes the person's answers to the capability's `asks` (D112): checked against the asks, merged into the approved input and named in the approval's audit row ([what a write asks](protocol.md#what-a-write-asks-and-what-it-says-it-will-do)).

**Limits and pending work.** Real-system pilot choice, live CalDAV regression of the new path and the full process-death matrix remain open. Unknown effects are not blindly replayed.

**Evidence.** [Card decisions](../../../apps/server/src/threads/usecases/decisions.ts), [calendar decisions](../../../apps/server/src/modules/calendar/usecases/decisions.ts), [D45](../../decisions/D45-approved-intent-precedes-source-dispatch.md), [database proof](../../../tests/db/postgres-calendar-decisions.test.ts)

## Jobs across systems

**Works in this checkout.** A connector declares the facts it creates (`facts`, `creates`) and the proposals that follow a fact kind (`follows`, taking a `FactEnvelope`, returning a `FollowResponse` whose steps name the follower's own connector); an administrator binds followers to a kind in the database (default deny); Clew assembles one job proposal by fan-out, names every bound system's outcome, and approves it once: one execution row per execute step, a bounded watch per watch step with its timer intent (`watch_intent`), undo-all as one linked compensation per step, all in one transaction with audit and the workflow starts (D86). One `jobWatch` workflow per watch step starts with that commit; it waits for each committed check, calls the fenced `observe` activity (read as the person, `seen` ends the watch, a revoked authority leaves it `blocked`), and at the window's end settles `expired`, which leaves one card for the person through the stream's attention admission.

**Limits and pending work.** Thin routes only (`POST /api/jobs/assemble`, `POST /api/jobs`, `GET /api/jobs/:id`): no card UI, panel step list or administration page for bindings; the job and its watches exist as ledger rows, audit, the API's view and the expired watch's generic pushed card. Bindings are made with `bun scripts/job-bind.ts` (or `--fixtures` for the development fixture offer) until the admin page has them. The independent fixture connectors declare the offer (`hr:absence`; `hr.proposeAbsence`, `timesheet.followAbsence`, `payroll.followAbsence`): payroll reads HR's authenticated HTTP feed and exposes reports dated before today, so a report made today is watched until the window ends. A watch is approved once and never replaced (generation 1); there is no cancel of a running watch. Fact-kind drift is judged at assembly (degraded bindings named in the proposal), not yet on the administration page. The full composer/pushed entry paths and receipt-driven facts assembling the next proposal remain planned; `creates` does not automatically start another job. See [planned continuation](../../architecture/working-across-connectors.md#planned-continuation-after-a-result). [D77](../../decisions/D77-job-approvals-preserve-intent-bindings-and-receipt-authority.md) closes the reproduced approval/read gaps: retries retain the original watch schedule, approval rechecks current binding revisions and per-binding limits, and receipt paths require the original unit/authorization version plus current capability access. Clients echo step `binding` and source `bindingRevision` from assembly; old unapproved proposals need reassembly. Immutable server-side reviewed proposals and creator-schema validation of facts remain unimplemented.

## Scan occurrence lifecycle

**Works in this checkout.** Persisted source key/assignment/period/revision, local dismissal, source-isolated coalesced refresh, stale-result fencing and authoritative completion. Partial/unavailable scans cannot infer completion by absence. Source cards retain their original person/grant version; transfers and renewed grants cannot read old snapshots. Fresh scans create separate authorized projections.

**Limits and pending work.** Legacy source cards without provenance are hidden after migration 0034; source-only ACL changes need a revocation path into Clew before persisted scans are enabled ([D75](../../decisions/D75-source-snapshots-retain-the-authority-that-produced-them.md)). Legacy topic-only scans stay conservative. Calendar's demonstration planner keeps its own proposal lifecycle.

**Evidence.** [Refresh](../../../apps/server/src/threads/usecases/refresh.ts), [tests](../../../tests/unit/refresh.test.ts), [D47](../../decisions/D47-occurrences-timers-and-attention-have-durable-identities.md)

## Timers

**Works in this checkout.** Transactional absolute timer intents, generations, cancellation and current-authority checks; every intent starts its workflow inside the transaction that commits it (D86: `dbos.enqueue_workflow` on the ledger's own connection, no outbox loop). The durable engine (DBOS Transact in the server process, D85) owns new and queued legacy jobs. A job's watch step is a bounded conditional watch: committed absolute checks and an end, read as the person, settled in the ledger (see Jobs across systems).

**Limits and pending work.** Legacy running jobs require operator drain evidence. The watch is the one conditional timer: no general "tell me when X" outside a job, no cancel of a running watch; a live delivery deadline is not established. The retired outbox tables and columns remain as evidence until a later schema change drops them.

**Evidence.** [Workflows](../../../apps/server/src/dbos/workflows.ts), [D85](../../decisions/D85-dbos-transact-replaces-temporal-as-the-durable-engine.md), [D86](../../decisions/D86-the-ledger-starts-its-workflow-inside-its-own-transaction.md), [runtime proof](../../../apps/server/tests/timer-runtime.test.ts), [watch runtime proof](../../../apps/server/tests/watch-runtime.test.ts), [rollback proof](../../../tests/db/postgres-store.test.ts), [operations](../../maintainers/reliability-operations.md)

## Review recovery and completion

**Works in this checkout.** Submitted reviews remain openable from the card and Klart after undo expires. Optional connector-declared text corrections use the human execution ledger and reload the reviewed version only after confirmed success; a source link is the fallback. A deterministic new card retries rejected rows only, preserving the original receipt and confirmed writes. Unknown outcomes require reconciliation. Shared completion feedback covers reviews, receipts and successful saves; undo errors remain visible and status checking retains its controls.

**Limits and pending work.** Corrections currently support up to 12 bounded text fields, not arbitrary forms. The finance fixture demonstrates missing-order rejection, correction and retry; its source URL is a placeholder. Current documents are shown beside the original receipt, not an archived copy of the submitted bytes.

**Evidence.** [D80](../../decisions/D80-recover-rejected-rows-without-replaying-confirmed-writes.md), [recovery guide](../../guides/document-and-semantic-views.md#reopen-correct-and-retry), [browser scenarios](../../../tests/a11y/documents.spec.ts), [retry scenarios](../../../tests/unit/threads.test.ts)

## Becoming done

**Works in this checkout.** When a receipt arrives the row keeps its place for 2,5 s in its receipt state (the check, the headline, Ångra), then goes to Klart, and a toast with Visa and Ångra says so; a connector may mark an execute `review: 'each'` with a `preview` read, and the work item's next step `Granska N` (and each document under its "Dokument") then leads to the review's own page, `/items/<threadId>/review` with the step as `step` and the page the item was shown on as `from` (D73, amended 2026-11-12 under the product owner's rule that a task a person works through is a page): the trail back, the title and the progress (a Stepper below five rows, a ProgressBar from five) in the header, one row at a time with its document, "Hittills" beside it (under it at 1024 px and below), the decision's buttons and Skicka in the footer, the page stacked on a phone; it writes once at the end and leads back to the item where it was shown, with the receipt and Ångra. The decisions are the person's draft for the session (session storage per work item, `apps/web/src/review-session.ts`): a reload, Back and Forward, or a way out and back keep them, the item then says "Fortsätt granska" and shows them as its ticks, and the draft is cleared on Skicka, when the reviewed rows change, and when the session ends; the review's evidence is never kept, so after a reload Skicka reads the approved rows' documents again and sends only the versions the approvals were taken on. Back from the page puts the focus on the control that led there. The overlay's address (`?review=<threadId>&step=` on any page) and `/cards/:threadId/review` lead to the page; a decided item keeps its receipt, with Ångra while it can be undone. The finance fixture now provides original PDF invoices, DOCX agreements and XLSX specifications through the versioned document reader; the legacy SVG preview remains available.

**Limits and pending work.** A draft lives in the tab: another tab or device does not see it, and a reload after the tab is closed starts over. Back after a reload of the review lands on the item without the focus on the control that led there (the browser loads that page anew). Where "Fortsätt granska" and a row under Dokument lead to the same step, the way back gives the focus to "Fortsätt granska". On a phone each step focuses its document heading; required documents must render before approval is enabled. The rail's count changes at once, not after the pause. Not verified with a screen reader.

## Att göra

**Works in this checkout.** [D112](../../decisions/D112-the-interface-is-rebuilt-on-astryx-templates-a-queue-one-detail-shape-one-panel.md) item 3, board Inbox, Astryx's `table-inbox` template, at `/todo`. Three piles as tabs that are links (`tab`: Behöver dig, left out of the address, `waiting`, `done`): what needs the person in Hem's former order (due, later, proposals, notices), what waits on others with what the person set aside under it (Inte nu, each with its own state), and what is done, newest first. A filter field (`filter`) and the system (`area`) narrow the rows and the count left is said. A row is one link with a state dot and its word, the title, why it is here, when it is due and the source. Choosing it shows the work item in the reading pane beside the list (`item`), at 55 % of the page's box and resizable (the pane at least 440 px, the list 300 px); the pane is the item's panel, with the conversation about it and the box while a model is configured; ✕ or Esc closes it and gives the focus back to the row. Below 900 px of box the item takes the whole surface as its page draws it, with the way back to the list; on a phone the rail is a drawer and the tabs are short words without counts. "Fråga Clew" makes the queue the thing, or focuses the box of the item in the pane. An item the person no longer has says so in the pane. A source not read yet is said above the rows; one that does not answer is said on its own open rows, "· kan vara gammal" at the end of the why line, and in the item's head with since when ("Kan vara gammal · Personalsystemet svarar inte sedan 14:32"); an empty pile then waits and names the system, and it is spoken once in the session ([D116, amended 2026-11-12](../../decisions/D116-a-panel-is-a-peek-at-one-thing-a-list-is-a-page-and-every-view-has-an-address.md)). Hem's tabs and area from before (`/?tab=`, `/?area=`) lead here; a work item alone in Hem's address (`/?card=`) is Hem's own since 2026-11-12, beside Hem in its panel ([Hem under the box](interface.md#hem-under-the-box)). The rail's Att göra carries the count of what needs the person.

**Limits and pending work.** The rows are Astryx's `List`, not the template's `Table` (D112 gap 2), and the page measures its own width with the template's `ResizeObserver` (gap 4). "Mina ärenden" and the person's own action points are not piles here; they stay on Hem (D112, amended). The browser scenarios (`tests/a11y/queue.spec.ts`, a silent system's marks included) passed on routed data on 2026-11-12; no signed-in pass and no screen-reader pass.

## The work item

**Works in this checkout.** A work item has one shape at two widths ([D112](../../decisions/D112-the-interface-is-rebuilt-on-astryx-templates-a-queue-one-detail-shape-one-panel.md) item 4, the `work-item-detail` template): narrow in Att göra's reading pane, in the panel beside any page and in a conversation's answer; as a page at `/items/<threadId>` with the details rail (Detaljer, Berör, Öppna i källan), which at 1024 px and below is behind "Visa detaljer" in a fullscreen dialog, and on a phone with the next step pinned to the foot and the rest under Fler val (item 12). The header holds the source line, the title, the status (the queue's dot with its word), the badges (when it is due, its area, the one entity its rows name) and the buttons, with every earlier behaviour: one-press execute with its loading state, `confirm`, "Granska N", reads that unfold in the item, lead out, or, when they answer with a table or a list ("Se i personalsystemet" on a leave request), lead to the read's page with the item's page as the way back ([D116](../../decisions/D116-a-panel-is-a-peek-at-one-thing-a-list-is-a-page-and-every-view-has-an-address.md)), Inte nu, Påminn mig, Avfärda, Återöppna. The main column holds the receipt after a decision (each row read back with its outcome and source, Ångra with the minutes left), a notice's text ([D112, amended 2026-11-12](../../decisions/D112-the-interface-is-rebuilt-on-astryx-templates-a-queue-one-detail-shape-one-panel.md): an item whose execute is the person's read receipt leads with the draft's `summary` paragraph by paragraph, under no heading, then its first read with `target: 'link'` as the way to the whole of it, marked as leaving and not repeated among the buttons; the text stays after the receipt), "Varför ser jag detta?" (for a notice the provenance line alone: the source's reason and where and when the item came), the rows as Astryx's checkbox list with how many are chosen (not drawn on any item when their one row only repeats the title, with no detail, subject or choice), "Dokument" (each row's document leads to the review's page at that row) and "Händelser": what the person and Clew did, read from the item's own audit rows by `GET /api/threads/<id>/events` (only for an item the person may see; the person is "Du", nobody else is named, no model text), with Clew's planned reminder on top. Where Att göra's pane does not fit, `/todo?item=` draws the item as its page in place, with the way back to the list. In Swedish text the item is an "ärende" (headings, labels, toasts, errors, the server's own messages). `/cards/<threadId>` leads to the item's page.

**Limits and pending work.** The item carries no reference of its own (the boards' "EKO-2231") and no "your role", amount or cost centre: the protocol has no field for them, so they are not drawn. The rows' checkboxes are the selection for the action (`selectable`, `selected`); before a decision nothing is done, so the line says how many are chosen ("2 av 3 valda") rather than "klara", and no progress bar is drawn. A read the person opened is not recorded and is not in Händelser. The phone's bar holds the next step alone (the board draws two) so its words fit at 320 px. A notice's link out is the source's read with `target: 'link'`, so it is a button that asks the source for the address when pressed and opens it in a new tab, not a plain link; the notice's text is the draft's `summary`, which the protocol does not bound. The notice's layout passed its browser scenarios (`item.spec.ts`, `queue.spec.ts`, `hem.spec.ts`) on routed data on 2026-11-12. The calendar's proposals keep their own card (D112 item 9). A write whose `path` asks something or has an effect opens the action dialog from every place its button is drawn ([what a write asks](protocol.md#what-a-write-asks-and-what-it-says-it-will-do)); its receipt is the work item's. While the item's system does not answer, its head says it may be old and since when, and the dialog's last step, a `confirm` and a decision on its way say that what is sent is queued and read back (D116, amended 2026-11-12); an action with an `effect` read still cannot be sent while that read fails, since the step waits for it. The board's question box under Händelser is the panel's box ([D112 item 7](interface.md#the-panel-and-the-assistant-beside-a-thing)): in the reading pane and the panel beside a page; on the item's page "Fråga Clew" opens it. Not verified with a screen reader.

## Card actions in the browser

**Works in this checkout.** Avfärda, Inte nu, Ta upp nu and Ångra draw their outcome before the server answers and roll back with an error toast if it refuses; an execute action keeps its button loading until the decision has come to rest or four seconds have passed; a change notice waits for the person's own request.

**Limits and pending work.** The proposal card and Påminn mig keep the earlier presentation. Not verified with a screen reader.

**Evidence.** [D64](../../decisions/D64-a-card-shows-the-persons-own-action-at-once.md), [unit evidence](../../../tests/unit/web-optimistic.test.ts), [browser evidence](../../../tests/a11y/optimistic.spec.ts)

## Browser updates

**Works in this checkout.** Authenticated SSE invalidates the query cache using committed revisions; authorization changes clear retained state. Persisted attention budget/bundles and batch claims prevent repeated announcements across tabs.

**Limits and pending work.** At-most-once announcement can be lost after claim; the card remains. No push/email or live delivery SLO.
