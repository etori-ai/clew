# Implementation status: work, decisions and durable execution

One page of [implementation status](../status.md). Each entry says what works in this checkout, what limits it or is still to do, and where the code and tests that show it are.

## Approved writes

**Works in this checkout.** Generic card decisions and calendar create/move/cancel/confirm/undo use encrypted intent, transactional audit/card projection and workflow start (D86), read-back and linked compensation. Calendar API writes require a stable `decisionId` and return a pending card. A card decision takes the person's answers to the capability's `asks` (D112): checked against the asks, merged into the approved input and named in the approval's audit row ([what a write asks](protocol.md#what-a-write-asks-and-what-it-says-it-will-do)). An execute started about a person is approved with the user name the decision resolved for the person, and its approved digest carries the person (`subject`, migration 0056); dispatch sends it only while that user name is still the person's ([D122](../../decisions/D122-clew-keys-its-own-records-about-a-person-by-the-persons-id.md)). Otherwise, before anything was sent, it settles `failed` with the reason `subject-changed`: the work item says "Personen har inte längre det användarnamn som beslutet gällde. Inget skickades. Fatta beslutet igen." and its own button decides again under a new decision id, on the user name the person has now. After an attempt whose answer is missing it settles `unknown` with the same reason and is not sent again: "Personen har inte längre det användarnamn som beslutet gällde, så åtgärden skickas inte igen. Utfallet behöver kontrolleras i källsystemet." On a connector whose audience names a provisioned group, a member's approval is recorded and sent under the member's current groups, and one whose person has left the group by the time it runs is not sent (`authority-revoked`). An approved talk invitation takes a lock per invitee and is recorded on its proposal (migration 0056), so a second manager's confirmation of the same person is refused while the first may still be sent: running, pending (even with a blocking reason), or unknown, inside its approval's 24 hours, even if its manager leaves the team and can later return ([talks](people.md#utvecklingssamtal-talks)). When the calendar's own check right before sending finds the time or the room not free, or cannot read them, the invitation is not sent: its row says "Inget skickades: …" and the execution settles `failed`, not `unknown`.

**Limits and pending work.** Real-system pilot choice, live CalDAV regression of the new path and the full process-death matrix remain open. Unknown effects are not blindly replayed. An execute started from a person's menu is not sent to the new holder or under the new name when the person's user name moved before dispatch: when nothing was sent, the approver decides again, on the user name the person has now; after an attempt without an answer it is not sent again, and its outcome is to be checked in the source system.

## Jobs across systems

**Works in this checkout.** A connector declares the facts it creates (`facts`, `creates`) and the proposals that follow a fact kind (`follows`, taking a `FactEnvelope`, returning a `FollowResponse` whose steps name the follower's own connector); an administrator binds followers to a kind in the database (default deny); Clew assembles one job proposal by fan-out, names every bound system's outcome, and approves it once: one execution row per execute step, a bounded watch per watch step with its timer intent (`watch_intent`), undo-all as one linked compensation per step, all in one transaction with audit and the workflow starts (D86). One `jobWatch` workflow per watch step starts with that commit; it waits for each committed check, calls the fenced `observe` activity (read as the person, `seen` ends the watch, a revoked authority leaves it `blocked`), and at the window's end settles `expired`, which leaves one card for the person through the stream's attention admission.

**Limits and pending work.** Thin routes only (`POST /api/jobs/assemble`, `POST /api/jobs`, `GET /api/jobs/:id`): no card UI, panel step list or administration page for bindings; the job and its watches exist as ledger rows, audit, the API's view and the expired watch's generic pushed card. Bindings are made with `bun scripts/job-bind.ts` (or `--fixtures` for the development fixture offer) until the admin page has them. The independent fixture connectors declare the offer (`hr:absence`; `hr.proposeAbsence`, `timesheet.followAbsence`, `payroll.followAbsence`): payroll reads HR's authenticated HTTP feed and exposes reports dated before today, so a report made today is watched until the window ends. A watch is approved once and never replaced (generation 1); there is no cancel of a running watch. Fact-kind drift is judged at assembly (degraded bindings named in the proposal), not yet on the administration page. The full composer/pushed entry paths and receipt-driven facts assembling the next proposal remain planned; `creates` does not automatically start another job. See [planned continuation](../../architecture/working-across-connectors.md#planned-continuation-after-a-result). [D77](../../decisions/D77-job-approvals-preserve-intent-bindings-and-receipt-authority.md) closes the reproduced approval/read gaps: retries retain the original watch schedule, approval rechecks current binding revisions and per-binding limits, and receipt paths require the original unit/authorization version plus current capability access. Clients echo step `binding` and source `bindingRevision` from assembly; old unapproved proposals need reassembly. Immutable server-side reviewed proposals and creator-schema validation of facts remain unimplemented.

## Scan occurrence lifecycle

**Works in this checkout.** Persisted source key/assignment/period/revision, local dismissal, source-isolated coalesced refresh, stale-result fencing and authoritative completion. Partial/unavailable scans cannot infer completion by absence. Source cards retain their original person/grant version; transfers and renewed grants cannot read old snapshots. Fresh scans create separate authorized projections.

**Limits and pending work.** Legacy source cards without provenance are hidden after migration 0034; source-only ACL changes need a revocation path into Clew before persisted scans are enabled ([D75](../../decisions/D75-source-snapshots-retain-the-authority-that-produced-them.md)). Legacy topic-only scans stay conservative. Calendar's demonstration planner keeps its own proposal lifecycle.

## Timers

**Works in this checkout.** Transactional absolute timer intents, generations, cancellation and current-authority checks; every intent starts its workflow inside the transaction that commits it (D86: `dbos.enqueue_workflow` on the ledger's own connection, no outbox loop). The durable engine (DBOS Transact in the server process, D85) owns new and queued legacy jobs. Every scheduled job (the nightly scan, the nightly sign-in clean-up, the end of an undo window, a receipt's final state and an attention release) is a job row whose `scheduledJob` workflow starts in the transaction that writes it, and the engine runs it at its time through `scheduledJobRunner`; nothing polls the job table, and the polling scheduler is gone. A run renews its claim on the job while it lasts, so a run longer than the two-minute lease is never run twice beside itself, a job that stopped without completing is counted for the operator (`stalledJobs`), and a run still going after ten minutes is said in one error line and counted (`longRunningJobs`). The nightly scan runs 500 people to a page, each page a job of its own, so no run grows with the installation. A server's start takes over the last and the next night of the scan and of the clean-up, the later pages of the last night's scan included, when a deployment left them waiting under the replaced application version, so a deployment does not stop them and a night whose time fell during it runs late (D85 item 2, as amended 2026-11-13). `scripts/workflows-move.ts` lists and moves every other workflow left under an older version, from where its records end, and starts one that ended in `ERROR` again from the step that failed. A job's watch step is a bounded conditional watch: committed absolute checks and an end, read as the person, settled in the ledger (see Jobs across systems).

**Limits and pending work.** Legacy running jobs require operator drain evidence. Every other workflow that a deployment leaves waiting under the replaced application version (a reminder, an approved execution, a watch, a follow-up, a scheduled job other than the last and the next nights) runs only once an operator moves it with the script after the older processes have stopped ([after every deployment](../../maintainers/reliability-operations.md#after-every-deployment)); nothing moves it at start, since a start cannot tell whether those processes have stopped. Nothing times out a job's run: one that never settles holds its job until its process stops, so an operator restarts the instance that runs it ([operations](../../maintainers/reliability-operations.md#the-ledger-queue)). The watch is the one conditional timer: no general "tell me when X" outside a job, no cancel of a running watch; a live delivery deadline is not established. The retired outbox tables and columns remain as evidence until a later schema change drops them.

## Review recovery and completion

**Works in this checkout.** Submitted reviews remain openable from the card and Klart after undo expires. Optional connector-declared text corrections use the human execution ledger and reload the reviewed version only after confirmed success; a source link is the fallback. A deterministic new card retries rejected rows only, preserving the original receipt and confirmed writes. Unknown outcomes require reconciliation. Shared completion feedback covers reviews, receipts and successful saves; undo errors remain visible and status checking retains its controls.

**Limits and pending work.** Corrections currently support up to 12 bounded text fields, not arbitrary forms. The finance fixture demonstrates missing-order rejection, correction and retry; its source URL is a placeholder. Current documents are shown beside the original receipt, not an archived copy of the submitted bytes.

## Becoming done

**Works in this checkout.** When a receipt arrives the row keeps its place for 2,5 s in its receipt state (the check, the headline, Ångra), then goes to Klart, and a toast with Visa and Ångra says so; a connector may mark an execute `review: 'each'` with a `preview` read, and the work item's next step `Granska N` (and each document under its "Dokument") then lays the review over the page the item is on, in that page's own address (`?review=<threadId>&step=`; in Att göra beside `item`, `/todo?item=<threadId>&review=<threadId>`), as a drawer over the page and the item (on a phone a tall sheet over the item), one item at a time beside its document, writing once at the end and leading back to the page as it was with the card and its receipt, or with the decisions as the card's selection on ✕, Esc or the scrim (D111 rule 5; `/cards/:threadId/review` from before leads to the work item in Att göra with the review over it); a decided item keeps its receipt, with Ångra while it can be undone. The finance fixture now provides original PDF invoices, DOCX agreements and XLSX specifications through the versioned document reader; the legacy SVG preview remains available.

**Limits and pending work.** The review's decisions live in the drawer until it leads back: a reload of the review starts its decisions over (the step is kept). The drawer's ✕ is named "Stäng" (Astryx's own name), not "Stäng, Esc". On a phone each step focuses its document heading; required documents must render before approval is enabled. The rail's count changes at once, not after the pause. Not verified with a screen reader.

## Att göra

**Works in this checkout.** [D112](../../decisions/D112-the-interface-is-rebuilt-on-astryx-templates-a-queue-one-detail-shape-one-panel.md) item 3, board Inbox, Astryx's `table-inbox` template, at `/todo`. Three piles as tabs that are links (`tab`: Behöver dig, left out of the address, `waiting`, `done`): what needs the person in Hem's former order (due, later, proposals, notices), what waits on others with what the person set aside under it (Inte nu, each with its own state), and what is done, newest first. A filter field (`filter`) and the system (`area`) narrow the rows and the count left is said. A row is one link with a state dot and its word, the title, why it is here, when it is due and the source. Choosing it shows the work item in the reading pane beside the list (`item`), at 55 % of the page's box and resizable (the pane at least 440 px, the list 300 px); the pane is the item's panel, with the conversation about it and the box while a model is configured; ✕ or Esc closes it and gives the focus back to the row. Below 900 px of box the item takes the whole surface as its page draws it, with the way back to the list; on a phone the rail is a drawer and the tabs are short words without counts. "Fråga Clew" makes the queue the thing, or focuses the box of the item in the pane. An item the person no longer has says so in the pane. A source that has not answered is said above the rows. Hem's addresses from before (`/?card=`, `/?tab=`, `/?area=`) lead here. The rail's Att göra carries the count of what needs the person.

**Limits and pending work.** The rows are Astryx's `List`, not the template's `Table` (D112 gap 2), and the page measures its own width with the template's `ResizeObserver` (gap 4). "Mina ärenden" and the person's own action points are not piles here; they stay on Hem (D112, amended). The browser scenarios (`tests/a11y/queue.spec.ts`) passed on routed data on 2026-11-12; no signed-in pass and no screen-reader pass.

## The work item

**Works in this checkout.** A work item has one shape at two widths ([D112](../../decisions/D112-the-interface-is-rebuilt-on-astryx-templates-a-queue-one-detail-shape-one-panel.md) item 4, the `work-item-detail` template): narrow in Att göra's reading pane, in the panel beside any page and in a conversation's answer; as a page at `/items/<threadId>` with the details rail (Detaljer, Berör, Öppna i källan), which at 1024 px and below is behind "Visa detaljer" in a fullscreen dialog, and on a phone with the next step pinned to the foot and the rest under Fler val (item 12). The header holds the source line, the title, the status (the queue's dot with its word), the badges (when it is due, its area, the one entity its rows name) and the buttons, with every earlier behaviour: one-press execute with its loading state, `confirm`, "Granska N", reads that unfold in the item or lead out, Inte nu, Påminn mig, Avfärda, Återöppna. The main column holds the receipt after a decision (each row read back with its outcome and source, Ångra with the minutes left), "Varför ser jag detta?", the rows as Astryx's checkbox list with how many are chosen, "Dokument" (each row's document opens the review at that row) and "Händelser": what the person and Clew did, read from the item's own audit rows by `GET /api/threads/<id>/events` (only for an item the person may see; the person is "Du", nobody else is named, no model text), with Clew's planned reminder on top. Where Att göra's pane does not fit, `/todo?item=` draws the item as its page in place, with the way back to the list. In Swedish text the item is an "ärende" (headings, labels, toasts, errors, the server's own messages). `/cards/<threadId>` leads to the item's page.

**Limits and pending work.** The item carries no reference of its own (the boards' "EKO-2231") and no "your role", amount or cost centre: the protocol has no field for them, so they are not drawn. The rows' checkboxes are the selection for the action (`selectable`, `selected`); before a decision nothing is done, so the line says how many are chosen ("2 av 3 valda") rather than "klara", and no progress bar is drawn. A read the person opened is not recorded and is not in Händelser. The phone's bar holds the next step alone (the board draws two) so its words fit at 320 px. The calendar's proposals keep their own card (D112 item 9). A write whose `path` asks something or has an effect opens the action dialog from every place its button is drawn ([what a write asks](protocol.md#what-a-write-asks-and-what-it-says-it-will-do)); its receipt is the work item's. The board's question box under Händelser is the panel's box ([D112 item 7](interface.md#the-panel-and-the-assistant-beside-a-thing)): in the reading pane and the panel beside a page; on the item's page "Fråga Clew" opens it. Not verified with a screen reader.

## Browser updates

**Works in this checkout.** Authenticated SSE invalidates the query cache using committed revisions; authorization changes clear retained state. Persisted attention budget/bundles and batch claims prevent repeated announcements across tabs. A delivery that quiet hours or the day's budget defers commits with its batch's `attention-release` job and that job's `scheduledJob` workflow, and the engine makes the batch ready at its time; the release waits for a delivery of the batch still being admitted and releases it with the rest, and a delivery admitted after the release has claimed its job is written ready.

**Limits and pending work.** At-most-once announcement can be lost after claim; the card remains. No push/email or live delivery SLO.
