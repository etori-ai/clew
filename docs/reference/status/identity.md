# Implementation status: identity and access

One page of [implementation status](../status.md). Each entry says what works in this checkout, what limits it or is still to do, and where the code and tests that show it are.

## Users and identity

**Works in this checkout.** Users, login and grants are core (D62). People, units and groups enter through the SCIM 2.0 server at `/scim/v2` (D68) behind a provisioner's token; the grant is derived from D68's group keys and D85's group-to-capability mapping, audited and rewritten in the same transaction as the change; a first login binds the OIDC subject by `OIDC_BINDING_CLAIM` to exactly one provisioned person; the sign-in request also asks for `offline_access` when `OIDC_REQUEST_OFFLINE_ACCESS=true`, for an identity provider that gives a refresh token only then (written for a direct Microsoft Entra v2 client, which no installation has run yet); connector and model audiences match provisioned groups; Administration › Användare (`admin.users`) lists the people a page at a time, searched and narrowed by unit, role, status and capability on the server ([D100, the paged people list](../../decisions/D100-the-people-list-is-read-a-page-at-a-time-and-narrowed-on-the-server.md)), holds the mapping and shows when each provisioner last called, with a warning after two days of silence. A key written wrong is refused (D96), and so is a unit key for a unit another organisation holds ([D101, the provisioner's order](../../decisions/D101-a-provisioner-pushes-the-organisation-first-and-adds-before-it-removes-and-a-unit-belongs-to-one-organisation.md)); requests sent in parallel are serialised per person and per group; an administrator issues, replaces and takes back a provisioner's key on Administration › Användare, shown once and kept as a digest ([D107](../../decisions/D107-an-administrator-issues-replaces-and-takes-back-a-provisioners-key-on-the-users-page.md)), and `scripts/provisioner-token.ts` does the same from the app container, and `scripts/provisioner-check.ts` reads what a push left. The authorization fingerprint covers authority fields only, and the nightly scan runs for people who can sign in. Capabilities are the closed list `admin.connectors`, `admin.users`, `admin.appearance`, `admin.competence`.

**Limits and pending work.** The active grant is the one assignment the person acts as (no switching); one organisation per installation is what is supported, since any provisioner may push an installation-wide capability ([D101, the provisioner's order](../../decisions/D101-a-provisioner-pushes-the-organisation-first-and-adds-before-it-removes-and-a-unit-belongs-to-one-organisation.md), item 5); the `protected` key is refused at the boundary (D93), so nothing about it is stored, derived or shown; a silent provisioner is shown on the page but raises no alarm of its own, and there is no metric for it; a key answers until it is replaced or taken back, and a provisioner cannot be renamed; the first key of an installation still comes from the script in the app container; only the synthetic provisioner (`scripts/provisioner/`, run by `auth:setup` and `dev:provision`) has pushed to the server, so Entra's and Metakatalogen's behaviour is covered by tests, not a tenant; the seed still creates the three person rows with the ids the fixtures and calendars key on; the Administration entry shows for either admin capability.

## Organisation tree

**Works in this checkout.** Units form a tree (D99, the organisation tree). A `unit:` group names the unit above it in a SCIM extension, also a unit nobody is placed on; the server refuses a parent that is missing, in another organisation or would close a cycle, and the removal of a unit with units below it; a move is audited and changes nobody's grant; writes that change the tree are serialised. Administration › Organisation (`/admin/organisation`, `admin.users`) shows the tree with who leads each unit, how many are placed on it and in its branch and what a push left wrong, and a unit's people over it. The synthetic provisioner pushes five levels from the root down and removes from the leaves up; `provisioner-check` reports the tree and the units whose people report to nobody.

**Limits and pending work.** Nothing follows a branch yet: no audience that means everything below a unit, no figure summed over one, and a connector is told one unit and not the path above it. A unit holds an id, a name and a parent: no photograph of a manager, no validity dates. Only the synthetic directory has pushed a tree. axe's experimental `label-content-name-mismatch` is left out on the tree and 2.5.3 is checked row by row in its place; no manual screen-reader pass.

**Evidence.** [D99](../../decisions/D99-units-form-a-tree-pushed-over-scim-and-a-manager-works-with-their-direct-reports.md), [provisioner guide](../../guides/writing-a-provisioner.md), [page](../../../apps/web/src/pages/admin/organisation.tsx), [use cases](../../../apps/server/src/modules/people/usecases.ts), [tests](../../../tests/unit/organisation-tree.test.ts), [browser scenarios](../../../tests/a11y/organisation.spec.ts)

## User delegation

**Works in this checkout.** Manifest audience and session-backed token exchange; Eneo wrapper. On a connector declaring delegation, an approved write is dispatched and read back with the token of the person's session that approved it, while that session is active and theirs; the token is exchanged before the dispatch is recorded. A later session in which the person asks to check a sent write may stand behind its read-back only, never a dispatch or replay. A scan runs with the token of the session that last asked for the refresh (`X-Clew-Delegated-Token` on `POST /clew/scan`), only while the person has been active in that session within 15 minutes (`PRESENCE_MS`: sign-in or the page's last `POST /api/auth/activity`); a write has no activity bound. A person who comes back is scanned for on their next ask, which requeues a blocked request at once and clears its block. Session bindings are sealed in the execution and the refresh request (migration `0047_session_bindings`); audit rows name the session's role, never the binding or a token.

**Limits and pending work.** Figures, callbacks, the nightly scan and job watch steps get no delegated token. Without a live session (for a scan: one active within the window) a write stays pending with `needs-session` and a scan answers `authorization-required` (blocked, cards kept). A pending `needs-session` write is not resumed by a later sign-in; checked after 24 hours it fails as `approval-expired`. Not yet run against a real source or the development IdP (D101).
