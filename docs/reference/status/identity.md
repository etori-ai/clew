# Implementation status: identity and access

One page of [implementation status](../status.md). Each entry says what works in this checkout, what limits it or is still to do, and where the code and tests that show it are.

## Users and identity

**Works in this checkout.** Users, login and grants are core (D62). People, units and groups enter through the SCIM 2.0 server at `/scim/v2` (D68) behind a provisioner's token; the grant is derived from D68's group keys and D85's group-to-capability mapping, audited and rewritten in the same transaction as the change; a first login binds the OIDC subject by `OIDC_BINDING_CLAIM` to exactly one provisioned person ([Sign-in and sessions](#sign-in-and-sessions)); the sign-in request also asks for `offline_access` when `OIDC_REQUEST_OFFLINE_ACCESS=true`, for an identity provider that gives a refresh token only then (written for a direct Microsoft Entra v2 client, which no installation has run yet); a connector's or a model's audience that names a provisioned group admits its members on every path that serves a person (the menu, reads, scans, actions, the assistant's tools, model choices, jobs, entity pages and the composites), since the server hands the registry the person's groups with the published actor, and the groups never leave the process ([Remote connectors](protocol.md#remote-connectors)); an audience, a group-to-capability mapping and the people list's unit take a key of up to 512 characters, SCIM's own limit; Administration › Användare (`admin.users`) lists the people a page at a time, searched and narrowed by unit, role, status and capability on the server ([D100, the paged people list](../../decisions/D100-the-people-list-is-read-a-page-at-a-time-and-narrowed-on-the-server.md)), with each person's titles under the name, those of their current employments or, where none carries one, SCIM's `title`, shown and searched and never read for authority ([D110, a person's title](../../decisions/D110-a-persons-title-is-pushed-as-scims-title-and-kept-apart-from-the-role.md); [D114, employments and phone numbers](../../decisions/D114-person-profiles-show-employments-and-categorised-phone-numbers.md): the profile lists each current employment with its title and unit, every phone number the directory sent with its category, and the e-mail address; what Clew cannot read of them is left out, and an employment on a unit Clew does not hold is refused), holds the mapping and shows when each provisioner last called, with a warning after two days of silence. A search word is looked for in the name, the person's title, every employment's title, the user name and the e-mail, without regard to case. Each mapping row is named by its own group, and the group picker searches every group of the organisation on the server (`POST /api/admin/users/groups/search`), each match with its external id under its name and a search the server did not answer said in the field; a row whose group another organisation now holds is removed like a row whose group is gone. "Byt nyckel" while a replaced key still answers warns that confirming ends that key at once ("Den förra nyckeln slutar gälla direkt"). "Inläsning från katalogen" and "Behörigheter från grupper" are headings a screen reader lists; a removed mapping row gives the focus to the next row's "Ta bort", else the previous row's, else the group picker; and an overview that cannot be read is said without the page's empty states. A NUL in a unit id, a provisioner id or a search word names nothing (400, or an empty answer), never 503. The capability `people.directory` ("Vilka användare finns i min enhet?") lists the unit's active people from their placements, with the role each holds there, as Personal reads a unit. The authorization fingerprint covers authority fields only, and the nightly scan runs for people who can sign in. Capabilities are the closed list `admin.connectors`, `admin.users`, `admin.appearance`, `admin.competence`.

A key written wrong is refused ([D96, a key written wrong](../../decisions/D96-a-key-written-wrong-is-refused-at-the-scim-boundary.md)), and so is a unit key for a unit another organisation holds ([D101, the provisioner's order](../../decisions/D101-a-provisioner-pushes-the-organisation-first-and-adds-before-it-removes-and-a-unit-belongs-to-one-organisation.md)); requests sent in parallel are serialised per person and per group. An `add` or `replace` without a `value` is refused with 400 `invalidValue` on every user and group path, path-less and `title` included; beside a deactivation the refusal waits and the person is still deactivated ([D113](../../decisions/D113-a-deactivation-is-never-refused-for-what-stands-beside-it.md) rule 1), and an explicit `null` or a `remove` still takes away a key, a parent or an attribute Clew does not require (one it requires is refused with 400 `mutability`, and a group's members go with a `remove`, since a `null` there is refused). A `remove` that carries a `value` on `phoneNumbers` or on the employments is refused the same way, naming the filter or the `replace` to send instead. An e-mail entry whose value is absent, `null`, empty or only space is left out before the address is chosen, and a value that is there but is not text is refused; among work addresses the one marked `primary` comes first, and when a `POST` or `PUT` body or a `replace` of `emails` carries a blank work entry, a readable home address is published, while an `add` publishes nothing in its place. A filter on an address type Clew does not hold, and a write to a phone number's `display` or `primary`, answer 200 and change nothing (D113 rule 2 as amended). A group `PUT` that leaves `externalId` out, `null` or empty keeps the stored key, and a group `POST` without one is refused with 400 `invalidValue`. A `userName` with space at either end or a control character anywhere is refused with 400 `invalidValue`; a user name is stored in NFC and compared without regard to case under ICU's root collation (`und-x-icu`), so `Åsa.Öberg` and `åsa.öberg` are one name whatever locale the database was created with. A unit's parent with a NUL is refused naming the attribute, a `members[value eq …]` filter Clew cannot read is 400 `invalidPath`, and any method other than `GET` on the five discovery addresses answers 405 with `Allow: GET`. A group write derives its members' grants only when the group gives something (a key with meaning or a D85 mapping), reading the organisation's mappings once under a hold that a mapping change waits for; it moves `meta.lastModified` of every member whose User resource it changes, and its audit row names up to fifty people a `POST` put in or a `DELETE` took out, as a `PUT` or `PATCH` names those who came or went. A person's source key is unique only where there is one (a partial index), so a key change beside a group write no longer deadlocks. Among units on which a person holds the same role, the active unit is the one whose id comes first compared character by character, by UTF-16 code unit (`Skola` before `förskola`, `Z` before `a`), on either adapter.

An administrator issues, replaces and takes back a provisioner's key on Administration › Användare, shown once and kept as a digest ([D107](../../decisions/D107-an-administrator-issues-replaces-and-takes-back-a-provisioners-key-on-the-users-page.md)), and `scripts/provisioner-token.ts` does the same from the app container through the page's use cases and audit rows, so `provisioner.rotated` records a key a second rotation ended early (`endedEarlier`). `scripts/provisioner-check.ts` reads what a push left and warns of deactivated people still in `unit-manager:`, `capability:` or plain groups and of a `capability:` key outside the closed list. The example provisioner (`scripts/provisioner/`) deactivates leavers before it reads the organisation, records and skips a row the export has wrong or Clew refuses, with what depends on it, carries on with every other change and removal, and reports the skipped rows as a failed run, while a fault in the export as a whole still stops the run: one in the organisation (a unit or group id listed twice, a key Clew reserves on a plain group, a unit or plain group outside the writer's keys) after the deactivations, and one in the people rows (such as a person id, or an active person's account name, listed twice) before anything is written; it sends a leaver Clew holds under a name nobody else has once the run is done (the source's, else the one Clew holds, else the row's `externalId`), so people who held one name in turn are not refused once they have left; it tolerates a second writer (a row seen twice, a 409 on create, a 404 on delete), and a copy of the folder type-checks outside Clew with `packages/contracts/src/scim-group-key.ts` beside it.

**Limits and pending work.** The active grant is the one assignment the person acts as (no switching); one organisation per installation is what is supported, since any provisioner may push an installation-wide capability ([D101, the provisioner's order](../../decisions/D101-a-provisioner-pushes-the-organisation-first-and-adds-before-it-removes-and-a-unit-belongs-to-one-organisation.md), item 5); the `protected` key is refused at the boundary (D93), so nothing about it is stored, derived or shown; a silent provisioner is shown on the page but raises no alarm of its own, and there is no metric for it; a key answers until it is replaced or taken back, and a provisioner cannot be renamed; there is one kind of key, so the key the check is issued can write as much as a provisioner's, and if it is left behind, its row shows "Tyst i över två dygn" from two days after the check last called until it is taken back, which is why it is issued right before the check and taken back afterwards; past fifty people a group's audit row holds the count alone; the first key of an installation still comes from the script in the app container; only the synthetic provisioner (`scripts/provisioner/`, run by `auth:setup` and `dev:provision`) has pushed to the server, so Entra's and Metakatalogen's behaviour is covered by tests, not a tenant, and D100 (the paged people list) and D101 (the provisioner's order) stay provisional until a real directory and a provisioner outside the team have used them ([D102](../../decisions/D102-a-decision-is-provisional-until-something-outside-the-repository-has-tested-it.md)); the seed still creates the three person rows with the ids the fixtures and calendars key on; the Administration entry shows for either admin capability.

## Sign-in and sessions

**Works in this checkout.** A sign-in follows the identity provider's own session ([D115](../../decisions/D115-a-sign-in-follows-the-identity-providers-session.md), beside [D5](../../decisions/D05-oidc-and-oauth-only-identification-path.md)): the authorization request carries no `prompt` and no `max_age`, and an ID token without `auth_time` signs the person in; an organisation that wants a fresh prompt, on shared computers for example, sets it in the identity provider. A first login binds the subject to the one enabled, provisioned person whose user name equals the binding claim (`OIDC_BINDING_CLAIM`), in NFC and without regard to case under ICU. Every later sign-in compares the claim the same way: when it names another person than the one the subject is bound to, the sign-in is refused with `identity-conflict` and nothing is rebound, while a claim that names nobody, or no claim, does not refuse ([D68](../../decisions/D68-people-are-pushed-into-clew-through-standard-scim.md) item 6 as amended). Each `identity-conflict` writes its row in the authentication log and an `identity.conflict` audit row with the claim's value, the refused subject and the person who holds that subject, if anyone does; `login-denied` names the person when one is known. A first login reads the person and the grant in its own transaction, so first sign-ins at the same moment no longer hold every connection of the pool, and `/api/ready` answers 503 unless the database answers within a second. A session lasts through an identity provider that cannot be reached, times out, limits the rate or refuses the client: the person's requests go on, delegation answers 503 until a refresh succeeds, the session asks the provider again after 30 seconds, one warn line is logged at most once a minute, and no connection is held while the provider answers. Of a refresh's outcomes, only the provider's `invalid_grant`, `interaction_required`, `login_required` or `consent_required`, a refreshed ID token for another subject, a session row that is gone and sealed tokens that can no longer be opened end a session. Besides back-channel logout, Clew answers OpenID Connect Front-Channel Logout 1.0 at `GET /api/auth/frontchannel-logout`: with a `sid`, and an `iss` that is the configured issuer or none, every open session of that `sid` ends with a `frontchannel-logout` row; another issuer is refused with 400, and the answer is never cached. A sign-in that cannot start or fails at the callback, and a back-channel or front-channel logout that is refused, write one log line with scope `auth` that gives the error's name and code, the provider's OAuth error, the HTTP status and the messages of the error and its cause where a message cannot quote a value (such a message may name a claim or a parameter), never a claim's value, a token, the provider's description or a value a statement was given. Every night at 03:00 Stockholm the job `sign-in-cleanup` runs once on the durable engine, however many processes schedule it: sessions past either expiry are removed with their sealed tokens, and each that was still open gets an `expired` row in the authentication log; expired login transactions and logout receipts are removed too ([D117](../../decisions/D117-clew-empties-expired-sign-in-data-itself-and-a-leavers-retention-is-the-organisations-decision.md)). An operator moves a person to a new sign-in account, or releases their binding so that their next sign-in binds them again, with `scripts/identity-rebind.ts --person <id> (--subject <new subject> | --release) --operator "<name>"`; it refuses an unknown person and a subject another person holds, and writes the binding and one `identity.rebound` audit row (actor `operator:cli`, with the old and the new subject and the operator) in one transaction.

**Limits and pending work.** No rebind on a page and never an automatic one. The claim is compared at sign-in, never on each request, and refuses only when it names another person, so a binding made while an account name was moving between two people is refused from the next sign-in after the provisioner has moved the name in Clew, and only an operator's rebind or release settles it. Front-channel logout ends a session only when the identity provider's sign-out page, in the person's browser, loads the address in a frame with a `sid` (for Microsoft Entra ID, its front-channel logout URL and the `sid` optional claim); it is the browser, not the identity provider's server, that must reach the address, and without a `sid` nothing ends. Not run against Microsoft Entra ID; the development stack signs in through a local Keycloak, which keeps back-channel logout. The authentication log is kept for as long as the installation lives, since how long sign-in history is kept is the organisation's decision (D117). A night whose clean-up fails says so in one error line and leaves what is left to the next night.

## A leaver's record and its erasure

**Works in this checkout.** A deactivation clears nothing ([D68](../../decisions/D68-people-are-pushed-into-clew-through-standard-scim.md) item 1): the person can no longer sign in, and their record (user name, source key, title, e-mail, every phone number and employment), their memberships and their placements stay as the last push left them. How long a deactivated person's record is kept is the organisation's decision under its own archive and data-protection rules, not Clew's ([D117](../../decisions/D117-clew-empties-expired-sign-in-data-itself-and-a-leavers-retention-is-the-organisations-decision.md)); Clew keeps it until an operator erases it. `scripts/person-erase.ts --person <id> --confirm` erases one deactivated person. It refuses an id the people table does not hold and a person who is still active, writing no audit row. In one transaction it removes the person's memberships, placements, grant, sign-in bindings and sessions; clears every personal attribute (name, e-mail, phone numbers, employments, title); replaces the user name with the person id and drops the source key, so the row keeps only its id, which other records point at, and a later push of the same person creates a new record; replaces the user names, the source key, the sign-in subjects and the claim values that name the person with `[erased]` in the audit trail and the authentication log, keeping the events (D117 item 3 lists them); and writes one audit row `person.erased` (actor `operator:cli`, counts only). The runbook's procedure for one person runs `subject-erase`, `talks-erase` and `competence-erase` first and `person-erase` last; each names the person by id and refuses an id the people table does not hold. What is only sign-in machinery Clew empties itself every night ([Sign-in and sessions](#sign-in-and-sessions)).

**Limits and pending work.** No timer erases anyone: an operator runs the scripts when the organisation's retention decision says so. Erase only after the source has stopped sending the person, or its next run creates the record again. The audit trail keeps the events, with the person's id. A connected system keeps what it holds under the person's user name, and the rows' text on cards stays as the source wrote it ([Subjects on cards and their erasure](people.md#subjects-on-cards-and-their-erasure)).

**Evidence.** [D117](../../decisions/D117-clew-empties-expired-sign-in-data-itself-and-a-leavers-retention-is-the-organisations-decision.md), [D68](../../decisions/D68-people-are-pushed-into-clew-through-standard-scim.md), [runbook](../../maintainers/reliability-operations.md), [operations guide](../../guides/provisioning-for-operations.md), person erasure in `scripts/person-erase.ts`, with `tests/unit/person-erase.test.ts` and, on PostgreSQL, `tests/db/person-erase.test.ts`, [card erasure](../../../scripts/subject-erase.ts), [talks erasure](../../../scripts/talks-erase.ts), [competence erasure](../../../scripts/competence-erase.ts), [competence erasure on PostgreSQL](../../../tests/db/postgres-competence-erasure.test.ts)

## Organisation tree

**Works in this checkout.** Units form a tree (D99, the organisation tree). A `unit:` group names the unit above it in a SCIM extension, also a unit nobody is placed on; the server refuses a parent that is missing, in another organisation or would close a cycle, and the removal of a unit with units below it or a write that gives it a new key or takes its key away; a move is audited and changes nobody's grant; writes that change the tree are serialised. An `add` or `replace` without a `value` on a unit's key, on the unit extension or on its `:parent` is refused with 400 `invalidValue`, so only an explicit `null` or a `remove` takes a key or a parent away, and a parent with a NUL is refused naming the attribute; a `PUT` that leaves out the key of a unit with units below it keeps the key and the tree. Administration › Organisation (`/admin/organisation`, `admin.users`) shows the tree with who leads each unit, how many are placed on it and in its branch and what a push left wrong, and a unit's people over it; while the unit is not yet known the overlay is named "Enheten" and its people "Personer på enheten", and a unit id the server refuses (400) is said without a retry. The synthetic provisioner pushes six levels from the root down and removes from the leaves up; `provisioner-check` reports the tree and the units whose people report to nobody.

**Limits and pending work.** Nothing follows a branch yet: no audience that means everything below a unit, no figure summed over one, and a connector is told one unit and not the path above it. A unit holds an id, a name and a parent: no photograph of a manager, no validity dates. Only the synthetic directory has pushed a tree. axe's experimental `label-content-name-mismatch` is left out on the tree and 2.5.3 is checked row by row in its place; no manual screen-reader pass.

## User delegation

**Works in this checkout.** Manifest audience and session-backed token exchange; Eneo wrapper. On a connector declaring delegation, an approved write is dispatched and read back with the token of the person's session that approved it, while that session is active and theirs; the token is exchanged before the dispatch is recorded. A later session in which the person asks to check a sent write may stand behind its read-back only, never a dispatch or replay. A scan runs with the token of the session that last asked for the refresh (`X-Clew-Delegated-Token` on `POST /clew/scan`), only while the person has been active in that session within 15 minutes (`PRESENCE_MS`: sign-in or the page's last `POST /api/auth/activity`); a write has no activity bound. A person who comes back is scanned for on their next ask, which requeues a blocked request at once and clears its block. Session bindings are sealed in the execution and the refresh request (migration `0047_session_bindings`); audit rows name the session's role, never the binding or a token. While the identity provider cannot refresh the session's token, the session stays and delegation answers 503 until a refresh succeeds: a write that needs the token stays `pending` with `source-unavailable` (`unknown` once it was dispatched), as for a source that cannot be reached ([Sign-in and sessions](#sign-in-and-sessions)).

**Limits and pending work.** Figures, callbacks, the nightly scan and job watch steps get no delegated token. Without a live session (for a scan: one active within the window) a write stays pending with `needs-session` and a scan answers `authorization-required` (blocked, cards kept). A pending `needs-session` write is not resumed by a later sign-in; checked after 24 hours it fails as `approval-expired`. Run against one real source only, Nextcloud's Approval app through the development Keycloak ([Nextcloud Approval](connectors.md#nextcloud-approval), D101, the first real integration).
