# Implementation status: identity and access

One page of [implementation status](../status.md). Each entry says what works in this checkout, what limits it or is still to do, and where the code and tests that show it are.

## Users and identity

**Works in this checkout.** Users, login and grants are core (D62). People, units and groups enter through the SCIM 2.0 server at `/scim/v2` (D68) behind a provisioner's token; the grant is derived from D68's group keys and D85's group-to-capability mapping, audited and rewritten in the same transaction as the change; a first login binds the OIDC subject by `OIDC_BINDING_CLAIM` to exactly one provisioned person; the sign-in request also asks for `offline_access` when `OIDC_REQUEST_OFFLINE_ACCESS=true`, for an identity provider that gives a refresh token only then (written for a direct Microsoft Entra v2 client, which no installation has run yet); connector and model audiences match provisioned groups; Administration › Användare (`admin.users`) lists the people a page at a time, searched and narrowed by unit, role, status and capability on the server ([D100, the paged people list](../../decisions/D100-the-people-list-is-read-a-page-at-a-time-and-narrowed-on-the-server.md)), with each person's titles under the name, those of their current employments or, where none carries one, SCIM's `title`, shown and searched and never read for authority ([D110, a person's title](../../decisions/D110-a-persons-title-is-pushed-as-scims-title-and-kept-apart-from-the-role.md); [D114, employments and phone numbers](../../decisions/D114-person-profiles-show-employments-and-categorised-phone-numbers.md): the profile lists each current employment with its title and unit, every phone number the directory sent with its category, and the e-mail address; what Clew cannot read of them is left out, and an employment on a unit Clew does not hold is refused), holds the mapping and shows when each provisioner last called, with a warning after two days of silence. A key written wrong is refused (D96), and so is a unit key for a unit another organisation holds ([D101, the provisioner's order](../../decisions/D101-a-provisioner-pushes-the-organisation-first-and-adds-before-it-removes-and-a-unit-belongs-to-one-organisation.md)); requests sent in parallel are serialised per person and per group; an administrator issues, replaces and takes back a provisioner's key on Administration › Användare, shown once and kept as a digest ([D107](../../decisions/D107-an-administrator-issues-replaces-and-takes-back-a-provisioners-key-on-the-users-page.md)), and `scripts/provisioner-token.ts` does the same from the app container, and `scripts/provisioner-check.ts` reads what a push left. A person's positions (D108 item 5, 2026-11-12, migration 0056) are pushed as membership of `position:<code>` groups, the display name being the label: a code and a label and nothing else, tied to the person, derived in the same transaction as the change and audited as `positions.derived` when the set of codes changes. `position:` is the fourth reserved prefix and is refused when written wrong; a position by itself decides no access, though its group can be mapped to a capability like any other. Nothing shows a person's positions yet; the competence requirements read them. The authorization fingerprint covers authority fields only, and the nightly scan runs for people who can sign in. Capabilities are the closed list `admin.connectors`, `admin.users`, `admin.appearance`, `admin.competence`, `admin.boarding` (D124).

**Limits and pending work.** The active grant is the one assignment the person acts as (no switching); one organisation per installation is what is supported, since any provisioner may push an installation-wide capability ([D101, the provisioner's order](../../decisions/D101-a-provisioner-pushes-the-organisation-first-and-adds-before-it-removes-and-a-unit-belongs-to-one-organisation.md), item 5); the `protected` key is refused at the boundary (D93), so nothing about it is stored, derived or shown; a silent provisioner is shown on the page but raises no alarm of its own, and there is no metric for it; a key answers until it is replaced or taken back, and a provisioner cannot be renamed; the first key of an installation still comes from the script in the app container; only the synthetic provisioner (`scripts/provisioner/`, run by `auth:setup` and `dev:provision`) has pushed to the server, so Entra's and Metakatalogen's behaviour is covered by tests, not a tenant; the seed still creates the three person rows with the ids the fixtures and calendars key on; the Administration entry shows for either admin capability.

## Organisation tree

**Works in this checkout.** Units form a tree (D99, the organisation tree). A `unit:` group names the unit above it in a SCIM extension, also a unit nobody is placed on; the server refuses a parent that is missing, in another organisation or would close a cycle, and the removal of a unit with units below it; a move is audited and changes nobody's grant; writes that change the tree are serialised. Administration › Organisation (`/admin/organisation`, `admin.users`) shows the tree with who leads each unit, how many are placed on it and in its branch and what a push left wrong; a row leads to the unit's own page (`/admin/organisation/<unitId>`, amended 2026-11-12), which names who leads it, how many are on it, the unit above and the units below as links and the unit's marks, and lists its people as three groups (who leads it, the others on it, who reports to its managers from below) in a table, a list on a phone, under one search, each group 25 to a page with its page in the address. The drawer over the tree is gone, and its old address leads to the page. The synthetic provisioner pushes six levels from the root down and removes from the leaves up; `provisioner-check` reports the tree and the units whose people report to nobody.

**Limits and pending work.** Nothing follows a branch yet: no audience that means everything below a unit, no figure summed over one, and a connector is told one unit and not the path above it. A unit holds an id, a name and a parent: no photograph of a manager, no validity dates. Only the synthetic directory has pushed a tree. The unit's people are read whole for one unit and searched and paged in the browser; a unit of several thousand would want the server to page them, as Användare does. Going back to the tree opens it down to the unit just left and nothing else a person had opened in it. A person's title (D110) is not on the unit's page, since the unit's read does not carry it. axe's experimental `label-content-name-mismatch` is left out on the tree and 2.5.3 is checked row by row in its place; no manual screen-reader pass.

**Evidence.** [D99](../../decisions/D99-units-form-a-tree-pushed-over-scim-and-a-manager-works-with-their-direct-reports.md), [provisioner guide](../../guides/writing-a-provisioner.md), [page](../../../apps/web/src/pages/admin/organisation.tsx), [a unit's page](../../../apps/web/src/pages/admin/organisation-unit.tsx), [use cases](../../../apps/server/src/modules/people/usecases.ts), [tests](../../../tests/unit/organisation-tree.test.ts), [browser scenarios](../../../tests/a11y/organisation.spec.ts), [address and grouping tests](../../../apps/web/tests/organisation-model.test.ts)

## User delegation

**Works in this checkout.** Manifest audience and session-backed token exchange; Eneo wrapper. On a connector declaring delegation, an approved write is dispatched and read back with the token of the person's session that approved it, while that session is active and theirs; the token is exchanged before the dispatch is recorded. A later session in which the person asks to check a sent write may stand behind its read-back only, never a dispatch or replay. A scan runs with the token of the session that last asked for the refresh (`X-Clew-Delegated-Token` on `POST /clew/scan`), only while the person has been active in that session within 15 minutes (`PRESENCE_MS`: sign-in or the page's last `POST /api/auth/activity`); a write has no activity bound. A person who comes back is scanned for on their next ask, which requeues a blocked request at once and clears its block. Session bindings are sealed in the execution and the refresh request (migration `0047_session_bindings`); audit rows name the session's role, never the binding or a token.

**Limits and pending work.** Figures, callbacks, the nightly scan and job watch steps get no delegated token. Without a live session (for a scan: one active within the window) a write stays pending with `needs-session` and a scan answers `authorization-required` (blocked, cards kept). A pending `needs-session` write is not resumed by a later sign-in; checked after 24 hours it fails as `approval-expired`. Not yet run against a real source or the development IdP (D101).

## Protocol 2 authority

**Works in this checkout.** RS256 installation assertions, pinned public keys, separate callback grants, transport key, current governance checks. Protocol 1 rejected; protocol 3 current since D117, a break, with 2 still loaded for a window (shown as "Följer ett äldre protokoll", sent no `about`, held to the looser rules of 2). Every request assertion is bound to its request (D117): its `body` claim is the SHA-256 of the exact body and, on a capability's route, its `capability` claim that name; every connector in the repository verifies both. A call whose input names people or units carries `about` in that body, each key sent and how the actor stands to it, never in the callback grant. A read the installation makes itself (D119, additive to 3) goes to `/clew/installation/{name}` with an assertion that carries no actor (subject `clew:installation`, `caller: "installation"`), bound to its request; the registry keeps such reads apart from capabilities, so no person's path reaches them, and the verifier every connector carries tells the installation's assertion from a person's both ways.

**Limits and pending work.** Installations and connectors must upgrade together; this tree contains ongoing reliability work.
