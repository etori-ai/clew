# Implementation status: calendar

One page of [implementation status](../status.md). Each entry says what works in this checkout, what limits it or is still to do, and where the code and tests that show it are.

## Calendar

**Works in this checkout.** CalDAV adapter and core calendar paths. The Microsoft 365 adapter passes the same contract against a local fake of Microsoft Graph, which runs in-process in the unit suite and as the `graph` service of the base development stack, self-seeded, never imported by the server (D69, amended). The development directory is a mixed estate: Mikael's calendar is Microsoft 365 over the fake, Hillevi's and Hassan's are CalDAV; `CALENDAR_ADAPTER` binds everyone to one. The calendar's reads declare their output schemas and Swedish labels, and `calendar.rooms` is a declared table view that an administrator can put in the menu as Mötesrum. An event's `id` is the source's own handle and may be up to 1 000 characters: a Nextcloud handle is the base64 of its CalDAV path, over a hundred, and until 2026-11-11 the registry refused every `calendar.today`, `calendar.week` and `calendar.day` answer with an event in it for a person on Nextcloud, which left the model's calendar tools and the action dialog's day without data. A person's calendar account is the address Clew's directory holds for them (the provisioned `emails`, read with each binding, `UserReads.email`), never one made from how they sign in; a person the directory holds no address for has no calendar bound, and a binding is let go of before a new one is made, so an erased person keeps none. The CalDAV adapter asks the calendar server for the account's `calendar-user-address-set` (RFC 6638) when it discovers the calendar and binds it only when `mailto:<the directory's address>` is among those addresses, compared without case; otherwise the person has no calendar ("Ditt konto har ingen kalender kopplad."). An operator keeps the two in line: the address the provisioner pushes for a person (`emails`) must be one the calendar server holds for that person's account (in Nextcloud, the account's e-mail address), or Clew shows the person no calendar rather than another account's. An event with no organiser and no guests is the owner's own appointment: theirs, with its buttons, and organised by them; one with guests and no organiser is nobody's the calendar names, has no buttons and reads "Okänd" as its organiser. On Microsoft 365 an event is the person's own by Graph's `isOrganizer`, which knows the mailbox's aliases, for its buttons and for the check of a booking read back. The CalDAV adapter reads the time zones of an event another client wrote within that event's own file, never through a registry the files share: a TZID that names an IANA zone is read as that zone, even when the file defines it, since a definition a client wrote may be stale; a zone the file defines under another name is read from the file's rules; and an event whose zone has neither a known name nor rules is refused with "Mötet har en tidszon som kalendern inte beskriver." (said as such when the manager settles a talk's meeting) rather than read at a guessed time. A floating time (no zone) is a time in Clew's zone, Europe/Stockholm, whatever the server process's; on an overlap it is the earlier of the two (02:30 on 2026-10-25 is 00:30 UTC). A length in hours, minutes or seconds is exact time across a clock change and one in days or weeks is nominal (RFC 5545 3.3.6). An event with `RDATE` is recurring, as one with `RRULE` is, and is neither moved nor cancelled as one meeting. Only the event a read uses is parsed, so an unreadable exception of a series does not stop the series being read. A moved meeting is written in UTC, without its old zone or a length. Free-busy takes up to twenty people and rooms in one request on every adapter (`FREE_BUSY_TARGETS`), as Microsoft Graph's `getSchedule` does, so a booking's check of eight people and a room is one request; the planner asks for a larger team in parts of twenty. A date of the right shape that does not exist (`2026-02-30`) is refused as "Ogiltigt datum." by the day, the week, the free times and the redraw, and the calendar page opens on today. A talk's meeting is known in the calendar family by `CalendarEvent.talk`, which the server sets from the event ids of Clew's own standing invitations, never by a title (D133): the reader's own by the event's ref, its uid and its iCalUId, those that invite them by the uid and the iCalUId that every copy keeps. Microsoft 365 gives the invitee's copy an id of its own, so the booking stores the organiser copy's iCalUId (migration 0086). Clew's zone is fixed in the code; whether an installation sets its own is an [open question](../../maintainers/open-questions.md#the-calendar).

**Limits and pending work.** The Microsoft 365 adapter has not met a real tenant, and no delegated token reaches it, so it runs only in development. Today, the week and a day are drawn by the calendar family, not by a declared view (D32). No signed-in browser pass on the Microsoft 365 binding yet. A zone by reference has been read only from files written for the tests; Nextcloud expands the events of a list into UTC itself, so the adapter's reading of zones matters for a single event read back by its id. A floating time is the one case where the two differ: Nextcloud expands it in the calendar's own `calendar-timezone`, UTC when none is set, while a lookup by id reads it in Clew's zone, so the same meeting can stand an hour or two apart in the week and in its pane. Clew does not create the calendars and does not set their zone; an operator gives each calendar Clew's zone (Europe/Stockholm) where clients write floating times. An event that names a zone neither defined with rules nor known by name stops the read it is in.

## The calendar page

**Works in this checkout.** [D112](../../decisions/D112-the-interface-is-rebuilt-on-astryx-templates-a-queue-one-detail-shape-one-panel.md) item 9, board Calendar. `EventCalendar` (D27, D32) draws an entry as a button only where the host passes `onItemClick` and as a link where it passes `itemLink` (WA-M2); its grid and its views are otherwise as they were. Kalender keeps its own page ([D126](../../decisions/D126-one-page-per-thing-one-astryx-template-per-page-type.md), D27). An event or a proposal chosen in the grid opens in the page's own pane in the end slot (`entry` in the address; an address that names the meeting of the manager's own talk opens the proposal the meeting is drawn as, `entryOf`), the drawer over the grid below 1340 px, on a short screen and on a phone: a meeting with when it is and, unfolded, where, who organises it and who comes, "Du är inbjuden" when the person does not organise it, and "Flytta …" and "Ställ in …" on a booking of their own (the entry's dialog, opened at that step); a proposal with "Förslag, inte bokat", the round's last day, when and with whom, and its existing decisions: "Skicka inbjudan" for that time, "Flytta …" (the dialog; drag is never the only way), "Föreslå andra tider", "Ångra" while the calendar allows it, and its name in the pane's header is the link to its work item's page. "Förslag N" in the header lists the proposals that wait, each a link to its week with it open in the pane; "Fråga om veckan" (or om dagen, om månaden) and "Fråga Clew" on an entry lead to a conversation with the range or the entry beside it (D126 item 4); the pane has no box. When the calendar does not answer, the page's head says "Kalendern svarar inte" (since when, when known) with "Försök igen", the grid keeps the weeks it has read, and with nothing read it says the week cannot be shown rather than drawing an empty one; it is spoken once in the session. A person with no calendar (not switched on for them, or no account bound) gets the page's "Ingen kalender är kopplad till dig" with who connects one, and the pages' row draws Kalender only while the calendar is the person's to see ([D116, amended 2026-11-12](../../decisions/D116-a-panel-is-a-peek-at-one-thing-a-list-is-a-page-and-every-view-has-an-address.md)). An entry is a control only where pressing it does something: a button in Kalender's grid and in the pane beside a conversation, a link to its place in Kalender (`/calendar?date=…&view=…&entry=<id>`) on a calendar read's own page (Dagens möten, Hela veckan, En dag), and no control at all, with no tab stop, in the action dialog's day, the event dialog's day and the week in a conversation's transcript; the spoken summary says "Retur på en post öppnar den." only where it does.

**Limits and pending work.** A meeting someone else organises has no buttons: the calendar source offers the invitee no reply of their own, so "Ändra mitt svar …" (the board) is not drawn, and the person's own answer is not shown. An answer that proposes a time is not drawn in the grid: the calendar family can draw a time not yet saved (`agendaItems`' `chosen`), but an answer carries no time as data unless it is an action's draft, and a draft belongs to a work item, not to the calendar; the grid is left as the calendar reads it. On a phone the head is the title and, under it, the steps with the view menu and Förslag with Ny bokning: two rows of controls from 360 px and three at 320 px while proposals wait ([D74, amended 2026-11-23](../../decisions/D74-one-page-header-for-every-surface.md)); it has no "Fråga om veckan", and an entry opened there is the drawer over the grid. The browser scenarios (`tests/a11y/calendar.spec.ts`) passed on routed data on 2026-11-12; no signed-in pass on the development stack and no screen-reader pass.

## Calendar follow-up

**Works in this checkout.** Approved bounded policies, two reminders maximum per invitation, two working days apart, 30-day expiry, current assignment checks and transactional invitee cards/counters/audit. An invitee is found by the person's id, which a proposal stores beside the address it was drawn with (migration 0056), so a changed work address keeps the reminders, the booking and the round's count. Confirmation and dispatch each check that only the invitee holds the drawn address in the manager's current team. If that check fails, the manager can draw new times with the current address. Replies to a sent invitation are matched on the address it used.

**Limits and pending work.** Legacy invitations are paused for review; no implicit authorization for new automatic policy.
