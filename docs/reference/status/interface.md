# Implementation status: pages and appearance

One page of [implementation status](../status.md). Each entry says what works in this checkout, what limits it or is still to do, and where the code and tests that show it are.

## Theme and logo

**Works in this checkout.** An installation's colours and header logo are saved in Clew's database on Administration › Utseende (`admin.appearance`, D98) and read by every browser from the public `GET /api/appearance`, the sign-in page included; no build variable and no restart. A theme is a Design Tokens (`.tokens.json`) file of Astryx's semantic colour tokens for the light and dark appearance, or two colours the page makes one from; a file is refused, with every problem named, when it sets an unknown colour or fails the WCAG contrast pairs. The logo is a stored PNG or SVG with an accessible name; an SVG with active content is refused. Each change is audited. The embedded `<site-header>` reads the same appearance through `appearance-src`.

**Limits and pending work.** Colour only: no typography, radius or component overrides from a file. No picture of the stored logo on the page (Astryx has no image component); no colour picker. Not exercised signed in against the development identity provider, and no manual screen-reader pass. Several instances would each need to re-read the row; a browser re-reads it on every visit.

**Evidence.** [D98](../../decisions/D98-the-installations-theme-and-logo-are-saved-in-clew-by-an-administrator.md), [branding guide](../../maintainers/branding.md), [theme file](../../../packages/contracts/src/theme-file.ts), [use cases](../../../apps/server/src/modules/appearance/usecases.ts), [tests](../../../tests/unit/appearance-admin.test.ts) The same changes are made from the command line with `bun scripts/appearance-set.ts <folder> | --reset | --show`, and `themes/sundsvall/` is an example folder with a theme file and a logo.

## Shared header

**Works in this checkout.** `packages/site-header` (D87, D88): one Astryx header for the web app and the intranet, drawn above the web app's rail as a band with the logo and the site's name, the reminder bell and the person, the places under them, and the current place's own pages under the band; the intranet loads `<site-header>` (`bun run build:site-header`), rendered in a shadow root with the same theme and band. The places, their pages, the site's name and the logo come from the one connector an administrator chose with "Ger sidhuvudet" on its page among those whose manifest declares `header: { capability }` (`Governance.header`, exclusive, audited; `Registry.header`, `GET /api/header` for the signed-in person), else Clew's default with Start alone. Start and the row under it are Clew's whatever the connector lists ([D116](../../decisions/D116-start-and-the-row-under-it-are-clews.md)): the server puts Start first, with Hem, Att göra, Kalender and, for a manager, Personal and Dialogstöd (`/units`, the overview of the units they follow up, D117) under it, and leaves out a place the connector calls `start` or that leads to `/`. The holder is asked as the person with their provisioned groups, so an audience that names a group decides who gets its header; it answers under a three-second budget, and its answer is kept in the process per person, authorization version and set of groups, served again for a minute and then once more while a fresh one is read. A holder that refuses the person (the protocol's `denied`, with its 403) has answered that it lists nothing for them: the default takes the place of what was kept at that answer and is kept until the next refresh, so a content system takes a person's places away as fast as it narrows them, and the conformance check takes such a refusal for one of its people as the holder's answer. A holder that fails, its 401 for Clew's key or assertion included, does not answer in time or answers out of shape leaves the last good answer in place for up to an hour after it gave it (`HEADER_STALE_MS`), or the default when it has given none, and is asked again a minute later; after the hour the default stands until the holder answers. An answer is kept whatever was kept while it was asked, and a failure takes nothing's place, so of two reads at once the one that fails cannot undo the other's answer. Who may have the header is decided at every read, without asking the holder (`Registry.headerHolder`): when the holder is switched off as the holder or another is chosen, its audience narrowed to leave the person out, or the connector or its header capability switched off, what was kept is dropped at the next read, and so is it when the registry refuses the holder's answer because one of these changed while it was asked, judged on the governance read after the call whether the holder answered or not. A refusal by the registry is never kept, so a person let in gets the header at the next read (D88, amended 2026-11-13). `connectors/intranet` is the development fixture (port 4049), answering the menu, logo and site name from `connectors/intranet/menu.json` (or `INTRANET_MENU_FILE`, with an optional `roles` per place), and `denied` for a person it lists no place for. The intranet may instead list its pages from Sitevision or WordPress through the embed's source adapters. The web app's dev server serves an intranet stand-in at `/intranat/`.

**Limits and pending work.** Not yet looked at signed in on the development stack; no screen-reader pass. The band is Vattjom, not the proof of concept's `#003c69`. No overflow menu (rows wrap). No editing of links or logo in Clew by decision: a connector owns the content, an administrator only chooses which. No Sitevision or SharePoint connector yet. The kept header lives in one process, so each instance keeps its own, and a header changed at the source, the source's refusal of the person included, reaches a person after the minute has passed, one page load later. While the holder is down, a person it has given nothing yet gets the default a minute at a time, and everyone gets it once the hour has passed.

## The panel and the assistant beside a thing

**Works in this checkout.** [D112](../../decisions/D112-the-interface-is-rebuilt-on-astryx-templates-a-queue-one-detail-shape-one-panel.md) items 7 and 8. One panel in the end slot (the drawer below 1336 px, on a short screen and on a phone), always about one thing: a work item, a view or a record, Kalender's event or proposal, or the page itself after "Fråga Clew". Its header names the thing (a work item keeps the small "Ärende" with its own title in the item; a calendar entry, the range and a page say their name with what they are under it, "Möte · Kalendern"), with ✕ and, once a conversation about it exists, "Fortsätt som samtal". Under the thing, the conversation about it drawn by the transcript of Hem's conversation (`ChatLayout`'s panel view), and at the foot the box, while a model is configured; without one the panel is the thing alone (D8). Asking starts or continues one conversation whose subject is the thing (a work item, a proposal or an event as its chip, a view or a tool by its capability; a person and a unit go without a chip, D97 item 7), kept under Samtal in the rail and reachable at `/conversations/<id>` with the thing beside it. Another thing in the panel's place starts with an empty transcript; a turn still on its way about the previous one is stopped and nothing is saved, and closing the panel lets the turn finish. While a conversation runs the thing's facts fold under "Visa allt" and its buttons stay. Opening a thing moves the focus to the panel's heading, never to the box; an arriving answer is spoken by the transcript's log. "Fråga Clew" (absent without a model) stands in the header of a work item's page, a person's and a unit's page, a tool's page (where it replaces the box at the foot), Att göra (the queue, or the box of the item in the reading pane) and Kalender ("Fråga om veckan", the range on screen); the address says so (`ask=1`). Att göra's reading pane is the item's panel: the item, the conversation and the box. An assistant's draft (D112 item 8) is drawn in the transcript with the action's name, "Utkast", the values and "Granska och …" and "Ändra", which open the action's own dialog at its last and its first step with those values; once sent the draft says "Skickat" with the receipt's headline, and a newer draft of the same action marks the older one as replaced. The server offers the model a draft tool only for the one work item a turn is about, listing the actions the person may take that ask for something; the values are checked as the decision checks them, kept in the conversation's message, never executed, and the turn's audit row names the action and the asks, not the values or the text.

**Limits and pending work.** "Fråga om veckan" sends the calendar's week read as its chip, so the model reads the week through its tool and is not told which week is on screen when it is not the current one. An event more than two weeks ahead goes without its chip (the server resolves an event among this week and the next). A conversation about a person or a unit tells the model nothing about them (D97 item 7). The conversation page shows the thing beside the transcript for a work item, a view, a tool, a proposal (its work item) and the week; an event, a person, a unit and the queue have no address of their own there. The panel's box has no `@`, no model menu and no verbs. The server scenario of drafts (`tests/unit/conversation.test.ts`) passes in `bun run check`. The browser scenarios (`tests/a11y/thing-panel.spec.ts` and the updated specs) passed on routed data on 2026-11-12. On a phone the panel is the end drawer with the page showing at its edge, not the sheet D112 item 12 draws. While a conversation runs, a work item's or a calendar entry's head (title, status, buttons) stands above the transcript and its facts scroll with it; on a short screen nothing is docked (D112 gap 10). No signed-in pass and no screen-reader pass.
