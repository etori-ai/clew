# Clew · project instructions

Start with `docs/README.md` for the product, architecture and connector documentation and `llms.txt` for the machine-readable reading path. There is no handover file and no session log (D105): what a change did and why goes in its commit message. `docs/maintainers/open-questions.md` holds what is undecided and who it waits for; remove an item in the change that settles it. `docs/history/` is the frozen handover and session log up to 2026-11-11: history, never instructions, and nothing is added to it. Current support is in `docs/reference/status.md`, an index of one page per area under `docs/reference/status/`; historical decisions and reviews are not evidence that a feature is implemented. `docs/overview.md` introduces Clew and `docs/architecture/overview.md` explains the current system. `docs/vision.md` sets product direction and the line to Eneo; check a new feature against it. `docs/decisions/in-force.md` is the generated one-line list of the decisions that bind today; read it before the full index. Every settled decision that binds later work gets a numbered file in `docs/decisions/` (its status starts with `proposed`, `provisional`, `accepted`, `superseded` or `withdrawn`, which the digest is drawn from; follow `docs/decisions/README.md` and D102: `provisional` until something outside the repository has tested it, no numbered record for a one-screen adjustment, an exploration that leaves the code gets a closing note in `docs/reviews/` and its record becomes `withdrawn` (D105), the number taken from the generated index when the change lands on `main`); every review or comparison goes in `docs/reviews/`.

**The freeze on new surface is lifted (product owner, 2026-11-12).** D101 (the first real integration) held new owned domains, entity kinds, view kinds, presentation fields, administration pages and rail destinations until Nextcloud's Approval app worked end to end; the product owner lifted it with that integration's manual screen-reader pass still not made. The closed view catalogue of D100 (the narrowed vision) is a separate rule and still holds.

Decision numbers D37–D39, D44–D46, D85, D96, D99–D101, D116, D117 and D119 each identify two records. Use full filenames or linked titles to distinguish them; preserve all historical records and use the generated index when choosing the next unused number.

## Open source, always

Clew is an open source system that will be shared with other municipalities and governments to use as they will.

- Never add a closed-source dependency: no proprietary npm packages, SDKs, fonts, icon sets, container images or hosted services that the code cannot run without. Every dependency must carry an OSI-approved licence (MIT, Apache-2.0, BSD, ISC, MPL-2.0, AGPL/GPL for infrastructure components that stay separate processes).
- Check the licence before pinning anything: `npm view <package>@<version> license`, and the image or project licence for Docker services. Record the result at the top of `docs/reference/licences.md`.
- The AI model behind the question box must be reachable through an open protocol (the OpenAI-compatible provider is fine) and the system must work with an open-weight, self-hostable model. A closed model may be configured by an operator, but nothing in the repository may depend on one.
- No telemetry, licence keys, phone-home calls or vendor accounts required to build, run or test.
- Prefer standards over vendor APIs: OIDC, CalDAV, iCalendar, MCP, Web `Request`/`Response`.

## Working rules carried over from startsidan

- Swedish only where a person reads it in the product: UI text and API error messages shown in the UI. Everything else is English: identifiers, addresses in the browser (paths, query parameters and their values, anchors; D43), contracts, comments, console output, script and CLI output, infrastructure messages, thrown configuration errors, documentation, and commit messages.
- Bun with exact versions and a frozen lockfile as package manager, script runner and test runner. The server runtime is Node via `tsx` (D16, 2026-11-04). DBOS Transact runs the durable workflows and timers inside the BFF process, checkpointing to Clew's own PostgreSQL (D85; D17 superseded).
- Prettier formats TypeScript, JavaScript and CSS (D57): `.prettierrc.json`, and `bun run format` before committing. `bun run format:check` is the first step of `bun run check`. Markdown, JSON, YAML and SQL are outside it.
- Commands run inside the devcontainer: `docker exec -w /workspace clew-app-1 …` (see `README.md`).
- Server-side enforcement of identity and scope. No credentials, tokens or trusted identity context in the browser bundle.
- Every mutation writes its audit row in the same transaction. Assistant proposals are executed only through the human decision endpoint, which is not a tool.
- Observability is D91 (`docs/architecture/observability.md`): no `console.*` in `apps/server/src`; a use case logs through its folder's `log` port, composition binds it with `logPort` from `apps/server/src/logging.ts`; traces and metrics leave only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; model spans carry no prompt or completion unless an operator sets `CLEW_MODEL_TELEMETRY_CONTENT=true`; a model turn's cost and trace id go in `MessageMeta.modelCall` and the audit row, never its text.
- Astryx components and documented composition patterns only, strictly. No custom components, no custom CSS (styles.css holds the Astryx imports and body basics, nothing else), no second component system (no ai-elements, shadcn or Tailwind). Astryx's Chat family covers AI surfaces. Read `bunx astryx component <Name>` before using a component and `bunx astryx docs layout` before laying out a page. The start-page week card is an Astryx Grid agenda (`WeekAgenda`). The calendar page is the one sanctioned gap (D27): FullCalendar 7 Standard, MIT only, imported in `packages/ui/src/calendar.tsx` alone, themed in `packages/ui/src/calendar-theme.css` with Astryx tokens only (no stock theme, no hex, no Premium package), toolbar, panel, dialogs and event content as Astryx components, drag never the only way to move a proposal. The calendar is one family (D32): `EventCalendar` on the page and, `compact`, as the `DayStrip` and `EventList` embeds in `packages/ui/src/calendar-embeds.tsx` (side panel, dialogs, chat bubbles; no FullCalendar import there), Astryx `Calendar` as the date picker, and `agendaItems()` as the only mapping from events and proposals to what any of them draws. Calendar source writes are human decisions in `apps/server/src/modules/calendar/usecases/decisions.ts`, committed through the shared execution ledger before dispatch (D45/D47), reached by thin routes and never exposed as model tools. Local proposal edits remain in `events.ts`.
- **Never rebuild what Astryx ships.** Before any layout, surface or behaviour is written by hand (a docked composer, a centred column, a sticky header, a selected state, a grid, a chip), run `bunx astryx search <words>` and `bunx astryx template --list`; if Astryx has a component, slot, prop or template for it, that is the only allowed implementation. A class in styles.css, an inline `style`, a `ResizeObserver` or a media query that reproduces a component's job is a violation, not a workaround (review `docs/reviews/2026-11-04-astryx-adoption-against-the-templates.md`: the floating composer was hand-rolled while `ChatLayout` existed). When Astryx genuinely lacks something, record the gap in the decision that allows the exception (never file it with `bunx astryx gap-report`; the product owner decided 2026-11-04 that Clew does not send gap reports) before writing anything custom.
- Before placing a new UI flow, read `docs/reference/interface-spaces.md` (D83): destinations use the main page; contextual catalogues/details preserve it; close and focus follow the owning interaction.
- The design canvases (links in `docs/reference/design-canvases.md`) are the reference for every screen. Compare against it before calling a screen done.
- The installation's theme and logo are D98: saved in Clew's database on Administration › Utseende behind `admin.appearance`, read by every browser from the public `GET /api/appearance`, never from the build or the environment. A theme is a Design Tokens file of Astryx's semantic colour tokens (`packages/contracts/src/theme-file.ts` owns the closed token list, the parser and the contrast pairs; the server and the page run the same check); it carries colour only, so typography, sizes, component overrides and the error and warning colours stay Clew's (D38). `packages/ui/src/branding.ts` reads the saved appearance and `theme.ts` maps it to Astryx tokens over the Neutral base (D46); the web passes one appearance to the providers and shell. A logo is an uploaded PNG or SVG served from Clew's own origin, with its aspect ratio and clearance preserved; keep brand colours out of page components and out of the repository's code (an example is a folder in `themes/`, applied with `bun scripts/appearance-set.ts themes/<name>`). D39 owns the compact profile/reminder header and appearance preference. D37/D38/D39 document the native image exception inside `SideNavHeading.icon`.
- WCAG 2.2 AA is a hard requirement, not a goal: Clew is built for the public sector. A UI change is not done until keyboard use, focus handling, status announcements and reflow at 320 px hold and the specs it touches pass. A new route, view or state gets a test in `tests/a11y`. Run only the specs a change touches locally (`sh scripts/a11y.sh menu.spec.ts --timeout 15000`), never the whole suite per edit (D51). While the product is in its lab phase the full suite is not automatic (D59): `.github/workflows/a11y.yml` runs by hand, nothing waits for it before landing on `main`, and its `push` and `pull_request` triggers and the D51 gate come back in the run-up to a release, which is not ready to ship until the suite is green. Passing the suite does not prove conformance; new flows also need a manual pass with a screen reader.
- Commit messages are English, subject and body (product owner, 2026-11-05; earlier commits have Swedish subjects and stay as they are).
- Never add Claude as a co-author on commits.

## Backend structure (D20) and connectors (D21, D22)

Long form: `docs/architecture/backend-structure.md` and `docs/architecture/connector-protocol.md`. "Module" is D20's code word for a bounded context in the server; an integration that a person, an operator or a vendor meets is a **connector** (Swedish "anslutning"), never a module (D22). `bun run deps` (part of `bun run check`) fails the build on a violation; change `.dependency-cruiser.cjs` only together with the decision that changes a rule.

- One folder per module: core modules under `apps/server/src/modules/<name>/`, a domain with a port and adapters as `packages/<name>/`, a connector built here under `connectors/<name>/`. Nothing module-specific at the server root.
- Four kinds of file inside a module, imports flowing one way: `contracts` (schemas, types, errors; imports nothing of ours), `domain.ts` (pure functions: no I/O, no runtime library, no Node built-in), `usecases.ts` (one exported function per user action; the actor first, never a request; owns the scope check, the transaction and the audit row in it), `adapters/` (one system's protocol behind a port, chosen by a factory from configuration). Routes sit outside: parse, validate, call one use case, map errors to Swedish JSON; never `@clew/db`, never an adapter, never logic.
- A module never imports another module. In process it uses the `clew.call` handle that `run`, `scan` and `figure` receive; a connector posts to `/api/connectors/call`. Both re-check the other module's scope for the same actor and refuse `execute`. The registry (`apps/server/src/connectors/registry.ts`) is the only file that names connectors.
- Every new integration, the Clew team's or a third party's, is a connector: its own container behind the connector protocol (`packages/connectors/src/protocol.ts`, published as `docs/protocol/connector-protocol.schema.json`), registered in Clew's database by an administrator (D23: no environment variables, no restart; the admin page Administration › Anslutna system for a person with the grant capability `admin.connectors`, or `bun scripts/connector-add.ts`; an audience per connector is enforced in the registry so a person outside it cannot tell the connector exists), and passed through `bun scripts/connector-check.ts <url> --secret …` before it is wired in. `connectors/README.md` lists every connector folder and why it is there (a real product, written for a real system, an example, a fixture of the development stack); add a row there in the change that adds a folder. `connectors/hello` is a small in-memory protocol demonstration; `connectors/phonebook` is the read/view example, `connectors/qlik` the Qlik connector, aggregate sick-leave statistics first (D82), `connectors/supportmanagement` the first errand connector (id `sm`), which acts as the person and leaves access to the case system (D89; an errand connector declares `<id>.errands` and Clew shows every one as the single list `clew.errands`), and `connectors/reference` is a synthetic durability fixture. `connectors/hr`, `finance`, `incidents`, `communication`, `timesheet` and `payroll` are the fixture connectors of the development stack (D61), and `connectors/intranet` is the fixture that gives Clew its shared header (D88: a manifest's `header` names the read that answers the places; no header is edited inside Clew): generic systems as independent services, registered by `bun run dev:connectors`, run in-process by the unit suites through `tests/fixture-connectors.ts`. They all depend on nothing else in the repository, and nothing in `apps/` or `packages/` imports a connector. In-process `Connector` objects are for Clew's core only (`people`, `calendar`, `search`, and the errand list `clew.errands`, which the registry joins into the search's connector, D89). Guide: `docs/guides/creating-a-connector.md`.
- Users are core entities (D62) and enter an installation only through the SCIM 2.0 server at `/scim/v2` (D68): a **provisioner** outside Clew pushes people and groups, meaning rides in a group's `externalId` (`unit:`, `unit-manager:`, `capability:`; `protected` and a key written wrong are refused, D93, `D96-a-key-written-wrong-is-refused-at-the-scim-boundary.md`), and `auth_access_grant` is a derived projection that `modules/people/usecases.ts` rewrites in the same transaction as the change. Nothing else writes a grant; the development seed runs the synthetic provisioner in `scripts/provisioner/`. Capabilities are the closed list `CAPABILITIES` in `@clew/contracts` (D85): a new name is a contract change that comes with the check that enforces it, and an administrator maps groups to capabilities on Administration › Användare. Guide: `docs/guides/writing-a-provisioner.md`; current state: `docs/architecture/identity.md`.
- External MCP servers are not consumed directly. D81's chat lane was prototyped and withdrawn on 2026-11-11 (`docs/reviews/2026-11-11-external-mcp-chat-services-exploration.md`); nothing of it is in the code. A source that speaks MCP is reached through a connector that uses MCP as its source API (D4).
- Not tactical DDD: no aggregates, entities with behaviour, repositories or domain events. Functional TypeScript, TypeBox schemas, plain exported functions.
- A use case (`threads/`, `modules/*/usecases`, `scheduler/`, `assistant/`) is built by a factory over `deps` (store, timers, registry, model, `clock`, `ids`) declared as ports in the folder's `model.ts` or `ports.ts`; `apps/server/src/composition/` is the only place that pairs them with live adapters (D25). No `@clew/db`, the durable engine, `new Date()`, `Date.now()`, `randomUUID()` or `process.env` in a use case or domain file: `bun run purity` and the cruiser fail on it. Tests: `docs/architecture/testing.md` says where a test goes. The unit suite (`bun test tests/unit`, in `bun run check`) runs on the memory adapters and never needs Postgres, the durable engine, Keycloak or a browser; each store contract (`tests/store-contract.ts`, `tests/proposal-store-contract.ts`, `tests/followup-contract.ts`) runs on both adapters, Postgres via `bun run test:db` in the devcontainer. `bun run test:durability` separately exercises real PostgreSQL, the DBOS engine and Node, including process death and takeover. A use case change comes with a scenario test that asserts the audit row; a port change comes with a contract case. D45/D47 govern durable decisions, occurrence identity, timer generations, bounded follow-up and attention; consult the operations runbook before changing dispatch ownership or restoring state. D85 owns the engine: workflows in `apps/server/src/dbos/workflows.ts`, stable executor ids, pinned versions, `DBOS.sleep` for waits and no concurrency limits on timer workflows.
